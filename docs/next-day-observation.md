## 1. 为什么这件事必须明天做

用户提供的这一条**不是观测结果，是设定知识**——它说明票据的有效期由服务端按天定义。
由此得出一条重要的回溯性判读：

**2026-09-15 全部六次启动观测（持当日票五次、旧票一次）只能证明「当天有效」，
不能证明任何持久性。** 它们与「一票管一天」完全一致，也与「一票管很久」完全一致——
**今日数据对该假设没有分辨力。**

判定必须在票跨过天数边界之后进行。

## 4. 弹窗判据（必须用这个，不要用标题）

**两层证据，缺一不可：**

**第一层——窗口 enabled 配对。** 弹窗存在时，同一进程内会出现一个模态窗口，
同时主窗口 `Enabled` 变为 `False`。因此判据是这一对：

```
主窗口 "KeySteam v2.99"  Enabled=False
  ＋ 同进程存在另一个可见窗口（"KeySteam 验证"）
```

**第二层——观测有效性前提。** 必须先确认窗口枚举**能列出主窗口**，
否则「没有弹窗」会被读成「没采到」。这是 drift 表登记过多次的错误模式。

**已知的观测限制**（务必遵守）：
- WSL 侧调用的 PowerShell **读不到完整类名与标题**（截断成 `title=[K]`），
  且 `EnumWindows` 回调可能完全不命中。**必须用独立 Windows PowerShell 进程运行监控脚本**，
  或用主窗口句柄直查 `IsWindowEnabled`（不受字符串读取限制影响）。
- 正常的窗口结构是 **6 个窗口、仅 1 个可见**。可见窗口数变为 2 是弹窗的信号。

## 5. 不要犯的错误（本项目已犯过的）

- **不要把「有到验证接口的连接」当作命中判据。** 实测确认该访问是**无条件**的
  （代理开启时经代理，关闭时直连），与票据是否有效无关。
- **不要把 `[IP]` 那行读成样本的连接。** 监控脚本的归集会把 `pid=0` 的 `TIME_WAIT`
  残留与活连接混在一起输出。要读的是**样本自己那行** `KeySteam(pid=N) -> 127.0.0.1:7890`
  或直连行，并核对 pid 归属。
- **不要用 `timeout` 包裹样本或宿主**——它杀不掉，会留下孤儿进程。
- **不要用 `Get-Process | MainWindowTitle` 单独判弹窗**——它每进程只报一个主窗口，
  会漏掉同进程内的模态对话框。

## 6. 三种可能的结果及判读

| 结果 | 判读 |
| --- | --- |
| 第二天启动**弹窗** | 「一票管一天」**成立**。当前路线**需要每日重做**——提交一次码，用一天。 |
| 第二天启动**不弹窗** | 「一票管一天」**不成立**（或票据被自动续期）。需查票据哈希是否在启动时被改写。 |
| 票据哈希**在启动前已变** | 样本或服务端有自行刷新机制，本轮观测对象已换，需重新设计判定。 |

**三种结果都有价值。** 第一种是用户已知的设定，能把它**确认到证据级**；
第二种会推翻设定，属于重大发现。

## 7. 若判定为「一天」，下一步

「提交一次码，用一天」意味着**每天需要一次人工干预**。这在工程上仍是可用的
（相比每次启动都要输码，已是显著改善），但用户若期望「一次到底」，则需要另立决策：

- 是否有办法让票据自动续期（需查样本是否支持，且这与 per-ticket ECDH 冲突）；
- 或者接受每日一次的输入成本。

**不要在本方案内预先假定结论**，先拿到明天的观测。
