| 搜索项 | 全 dll 命中 |

## 2. 静态完备性（为什么 r42 的闸门本身是对的）

从函数入口 `0x180FE8280` 严格解码（`.pdata` 区间 `0x180FE8280..0x180FE8813`，17863 个函数中唯一包含 GA 点者）：

```asm
0x180fe8564  test  r14, r14
0x180fe8567  jmp   0x180fe87ba      ← GA 补丁后（原 je 0x180fe864a）
0x180fe85a3  call  0x180fe0120     ← 唯一抛「验证已过期」的支路入口
0x180fe85db  mov   r8, [0x181DCB7E8]  ★ 过期文案槽
0x180fe85e2  call  0x1814164f0
0x180fe87ba  xor   eax, eax        ← GA 落脚 = 返回 NULL = 放行
```

**可达性穷举（三重）**：

| 检验 | 结果 |
|---|---|
| 分支目标落入 raise 区 `[0xFE856D,0xFE864A)` 的跳转总数 | **7 处，全部在同一函数内**，其中进入 `0xFE85A3` 的仅 `0xFE8590 je`（GA 已使其不可达） |
| 以 raise 区任一地址为**函数起始**的 `.pdata` 条目 | **0** |
| `main.dll` 导出表 | 仅 1 项，**无 Python C API 导出**（无法从外部注入） |
| 指向文案槽 `0x181DEB7E8` 的 rip-relative 引用 | **全局唯一** = `0x180FE85DB` |
| 全 dll `.data` 槽引用点统计 | 77,720 个槽 / 311,919 条引用，该槽只此 1 条 |

⇒ **r42 的闸门在逻辑上已封闭**，该文案不可能经启动闸门抛出。

## 3. 症状归属（诚实标注）

**未能复现**用户所报的 `[ 警告 ] 验证已过期`。四路独立测试均为阴性：

| 测试 | 环境 | 结果 |
|---|---|---|
| 干净 APPDATA + 穷举交互 | 独立 APPDATA | 弹窗帧 **0**、阻塞帧 **0**、`[ 警告 ] 验证已过期` **0** |
| **真实 APPDATA** + 穷举交互 | 用户实际数据 | 同上，**0** |
| UIA 精确坐标逐个按钮触发 | 真实 APPDATA | 障碍总数 **0** |
| 长时程多轮采样 | 真实 APPDATA | 见 §5 |

**双向对照证明判据有效**（非恒真）：

| 版本 | 弹窗帧 | 阻塞帧 | 判定 |
|---|---|---|---|
| 原版 `KeySteam.exe` | **28** | **28** | FAIL（必然命中「KeySteam 重要通知」） |
| r42 | 0 | 0 | PASS（但文案常量在内存中） |
| r44 | 0 | 0 | PASS |
| r45 | 0 | 0 | PASS |

**唯一残留差异**：r42 运行内存中存在 `验证已过期` 的 UTF-16 实例（CPython 对非 ASCII 字面量的内部表示），r44/r45 因替换了字面量而**归零**。该实例是**常量被加载**，非「已被渲染」——r42 静止态下同样存在，与是否点击无关。

**最可能的解释（按可能性排序）**：

1. **提示出现在运行日志面板**，用户在滚动日志时看到——`[ 警告 ]` 前缀与面板中 `[ 警告 ] 用户菜单尚未初始化` 完全同源。这种情况下**提示无害、程序照常可用**（本轮实测：主窗口全程 `en=True`）。
2. 用户实际运行的是**旧版本残留**（`D:\ks_debug\` 下存在 r40/r40final/r40x1/r40x2/r41_gatefix 等多个历史产物）。**r40 的 P2 补丁 `74→EB` 正是主动进入唯一过期支路的错误补丁**，见 `r42_DELIVERY.md` §4。
3. 触发路径依赖本机未复现的特定状态（如特定 Steam 用户 / 清单状态）。

## 8. 本轮方法论增量

1. **`[ 警告 ]` 类前缀必须搜片段**。日志级别前缀是 `"[ "` + 级别名 + `" ] "` 运行期拼接，搜完整串永远 0 命中，会误判为「文案不存在」。
2. **内存取证可一票确认补丁生效**。`OpenProcess + ReadProcessMemory` 直读 `main.dll` 基址 + RVA，比任何静态推理都硬。注意 FO≠RVA，`.text` 差 0x1000-0x400=0xC00。
3. **窗口枚举判据存在结构性盲区**。基于 `EnumWindows` 的验收看不到：日志面板文本、QTextEdit 内容、自绘控件。UIA 亦取不到 Qt `QTextEdit` 的 `TextPattern`。**这类症状必须靠截图直读**。
4. **双向对照不可省**。原版必然命中（28/28），补丁版必然零命中，判据非恒真/恒假——否则无法自证。
5. **等长替换是收口文本类症状的通用手段**。不改指令、不动控制流，仅替换字面量，风险最低、判定最直观。
