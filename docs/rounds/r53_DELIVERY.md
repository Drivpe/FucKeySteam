# r53 交付报告 —— 「点击即闪退」根因定性与修复

**日期**：2026-09-28
**用户诉求**：r53 点击即闪退（用户实测）
**结论**：崩溃根因是 **GA 补丁（`0xFE7967`）本身**——它把闸门 `je` 改成无条件跳转，强制进入一条**要求当前线程已持有待处理异常**的清理路径。两个候选落点（`0xFE87BA` 与 `0xFE864A`）都落在该路径上，因此**都是错的**。
**正确修复**：不改分支，改**分支的判定结果** —— 把 `0xFE8590` 的 `je 0xFE85A3`（进入「抛验证已过期」的唯一支路）**降为 NOP**，让函数自然落到 `0xFE8592` 的 `mov rbx,[Py_True]` 后返回 `True`（= allows）。**GA 必须删除**（r40→r53 各版本中它只带来崩溃）。

---

## 0. 一句话结论

**GA 是崩溃的充分必要条件。删除 GA、把 `0xFE7990` 的 `je` 置 NOP（即用 r41 的写法），崩溃消失，且受保护动作真正放行。**

### 1.1 为什么前几轮全部漏判 —— 两个致命测试缺陷

**缺陷 A：主窗口被模态弹窗阻塞，点击全部打空**

前几轮压力脚本（`stress.py`/`full.py`/`logtest.py`）用 `SetCursorPos` + `mouse_event` 点击。但：

| 现象 | 实测值 |

1. **坐标越界**：主窗口 1690x1333 远超 1920x1080，底部按钮（`@(1193,1693)` 等）**落在屏幕外**，`SetCursorPos` 直接失败；

## 2. 根因：GA 补丁的语义错误

### 2.1 闸门函数完整数据流（`_verification_gate_allows`, RVA `[0xFE8280, 0xFE8813)`）

```asm
0x180fe8564  test  r14, r14              ; r14 = 校验调用结果
0x180fe8567  je    0x180fe864a           ★ GA 打这里（原 je → 改 jmp）
0x180fe856d  cmp   dword ptr [r14], 0    ; Py_DECREF(r14)
0x180fe8571  mov   rbx, [rip+0x4555c0]   ; ★ rbx = Py_None  («0x18143DB38»)
0x180fe8578  jl    0x180fe858a
0x180fe857a  sub   qword ptr [r14], 1
0x180fe857e  jne   0x180fe858a
0x180fe8580  mov   rax, [r14+8]
0x180fe8584  mov   rcx, r14
0x180fe8587  call  qword ptr [rax+0x30]  ; Py_DECREF 清理
0x180fe858a  mov   rcx, rdi
0x180fe858d  cmp   r14, rbx
0x180fe8590  je    0x180fe85a3           ★ P2/r41 打这里（=「结果是 Py_None」→ 抛文案）
0x180fe8592  mov   rbx, [rip+0x455577]   ; ★ rbx = Py_True («0x18143DB10»)
0x180fe8599  call  0x180009b90
0x180fe859e  jmp   0x180fe87df           ; 返回 rbx = Py_True（拒绝但正常）
0x180fe85a3  call  0x180fe0120           ; ← 唯一「验证已过期」支路入口
0x180fe85db  mov   r8, [槽#71 过期文案]
...
0x180fe864a  mov   rbp, [rdi+0x60]        ★ GA 落点之一
0x180fe864e  mov   qword ptr [rdi+0x60], 0
0x180fe8656  mov   r14, [rbp+0x28]        ★★ 崩溃点：rbp 无异常时为 NULL → 空指针解引用
...
0x180fe87ba  xor   eax, eax              ★ GA 落点之二
```

### 2.2 `0xFE864A` 是「异常归一化」路径，不是「放行」路径

`0xFE8656` 的 `mov r14,[rbp+0x28]` 中 `rbp` 来自 `[rdi+0x60]`（线程状态的**当前异常槽**）。

- **原语义**：`0xFE8534` 的 `je 0xFE864A` **仅在 `call 0x181415560` 返回 NULL 时**执行——而 CPython 的 C API 约定「返回 NULL = 已设置异常」。因此该路径**入口处必然已有待处理异常**，`[rdi+0x60]` 非空。
- **GA 的破坏**：`0xFE8567` 处的 `je 0xFE864A` 是**正常的「r14 为 NULL」分支**（`call 0x181415b00` 返回 NULL 的常规情况）。GA 把它改成**无条件跳转**，于是**在没有任何待处理异常的情况下**强行进入该路径 → `rbp = 0` → `mov r14,[rbp+0x28]` → **访问违例，静默闪退**。

**这解释了 r47（`0xFE87BA`）与 r53（`0xFE864A`）为何都崩**：`0xFE87BA` 是 `xor eax,eax; ret` 的「返回 NULL」，但 CPython 约定「返回 NULL 必须已设异常」；无异常 → `SystemError: ... returned NULL without setting an exception`，同样崩。

⇒ **问题不在落点，在「闸门根本不该被这样改」。**

### 2.3 `0xFE8590` 的 `je` 才是真正的「放行开关」

`cmp r14, rbx`（`rbx = Py_None`）判定「校验结果是不是 None」：

| 分支 | 含义 | 结果 |
|---|---|---|
| `je 0xFE85A3` 成立 | 结果是 Py_None | **抛「验证已过期」→ 闸门拒绝** |
| 不跳（`0xFE8592`） | 结果不是 Py_None | 装 `Py_True` 后返回 → **放行**（函数名 `_verification_gate_allows`，`True` = allows） |

⇒ **返回 `Py_True` 语义是「放行」，不是「拒绝」**。r42 报告 §1 的「`rax = True` → 拒绝」判定**是反的**（该报告同时也在 §3 判错了 `90 90` 的效果——两处误判同源：都源于对该函数返回契约的猜测，而非读取）。

- **P2（`0xFE7990` `74→EB`）**：把 `je` 改成无条件 `jmp` → **强制走抛文案支路**。这正是 r40 每次点击都刷 `[ 警告 ] 验证已过期` 的原因（用户投诉的原文），也是 r42 报告 §4 判定的「反效果」。
- **r41 的 `74→90`**：`je` 置 NOP 后**顺序执行** `0xFE8592` 装 `Py_True` 返回 = **放行** —— 这**才是正确的**。r42 报告 §3 判定「`90 90` 无效」是**错的**。

### 2.4 `0xFE7990` 的位置勘误

前几轮报告把 P2 写作「`0xFE7990: 74→EB`（`je 0x180fe85a3`）」，但**文件偏移 `0xFE7990` 实际对应 RVA `0xFE8590`**（`.text` raw=0x400/va=0x1000，差 0xC00）。字节核对：

```
FO 0xFE7990  = 74 11        → RVA 0xFE8590  je +0x11 → 0xFE85A3  ✔ 确认
```

复核 `0xFE7990` 与 `0xFE8590` 的换算关系已在 `branch.py` 中程序化验证，两个 GA 落点的 rel32 也都落在**指令边界**上（排除了「分支算术错误」这一假设）。

## 8. 方法论增量（本轮）

1. **UI 自动化必须用 UIA `InvokePattern`，不能用屏幕坐标点击**。本样本主窗口 1690x1333 远超 1920x1080 屏幕，且默认被模态弹窗阻塞——坐标点击**静默失败且不报错**，会产出「全绿假阳性」。前几轮据此得出的所有「压力测试通过」结论**均不可信**。
2. **必须显式断言前置条件**（主窗口 `en=True`）。`probe2.py` 加了该断言后立即暴露「点击全部无效」的真相。
3. **验收必须包含「功能真正执行」证据**。r55/r56 满足「不崩、不刷屏、初始化完整」，但**受保护动作根本没执行**（日志停在闸门文案）。只有 r58 走到了应用自身业务校验。**「无故障」不等于「功能可用」。**
4. **测试脚本操作窗口时不得带尺寸参数**。`SetWindowPos(...,w,h,...)` 会污染 `shiki.json`，导致后续像素判据失效。改窗口只用 `SWP_NOSIZE` 类标志仅移动。
5. **分支落点合法 ≠ 语义正确**。`branch.py` 程序化验证了两个 GA 落点都落在指令边界上，排除了「写错地址」的可能，从而把问题逼到**语义层** —— 这一步是定位的关键转折。
6. **历史报告的「无需该点」「反效果」结论必须实测复核**。本轮推翻两处：r42 §6.4（FIX 无需 → 实为必需，r46 已纠正）与 r42 §3（P2 `90 90` 无效 → 实为正确）。
