## What to build

**第一次启动：让样本自己完成一次换票，并确认票确实落到了磁盘上。**

操作路径是手工的：启动 `KeySteam.exe`，等验证码弹窗出现，在弹窗里输入当日验证码，然后观测样本是否发起换票、是否把结果写进了缓存文件。

这一票**不追求免弹窗**。它的唯一目标是取得正面证据——证明样本走完了「提交码 → 服务端换票 → 落盘缓存」这条链。这是本路线唯一依赖样本正向功能的步骤，后续能否免弹窗完全取决于这一步是否真的发生了。

提交走手工而非自动化，是有意的：脚本化提交需要复现 `_validate_encrypted_code` 的「明文 → 加密 → KSP1」编码，而该编码的段落边界尚未定位。在未确证的机制上建自动化，会给一个本已清晰的验证引入新的不确定。

监控必须在样本启动**之前**就已运行。弹窗是模态的，若运行结果不佳，先开监控意味着它仍是被观测到的。

## Acceptance criteria

- [ ] 监控已先于样本启动，且日志文件已开始写入
- [ ] 样本启动后，观测到验证码弹窗出现（以窗口的 enabled 字段配对为判据：主窗口 `Enabled=False`，且存在同进程的模态窗口）
- [ ] 当日验证码已通过弹窗手工提交
- [ ] 观测到样本向 `key.steamofl.com` 发起连接，且该连接可归因到样本进程
- [ ] `verification.cache` 在提交后被创建或被改写（sha256 与第 0 步记录的基准不同）
- [ ] 样本已被正常关闭，且关闭后 `Get-Process` 无残留样本进程
- [ ] 本次运行的完整时间线与原始日志已存档
