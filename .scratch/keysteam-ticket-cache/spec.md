## Problem Statement

KeySteam v2.99 每次启动都会出现「验证码弹窗」（`VerificationDialog`）：它是应用模态的，主窗口虽可见但所有输入都被弹窗接管，且没有关闭按钮。要拿到验证码，得从号商的夸克网盘分享链接里下载当日的码。

前三轮的工作方向是**消除这个弹窗**（伪造缓存、注入、字节补丁）；第 5 轮一度转向**绕开 GUI 直接调用业务模块**。两条方向都已被证伪，且证伪理由在性质上不同：

伪造类方向与「票据是签过名的密文块、以每条票据一次性的 X25519 ECDH 封装」这一已确证事实正面冲突——本地不存在伪造路径。绕 GUI 方向则错在假设上：样本确实自带非图形入口，但该入口的入参 `--encrypted-ticket` 要的是 **Steam 客户端签发的 Encrypted AppTicket**，与号商的 KV1 票据是两条互不相干的链。绕过 GUI 不解决票据问题，只是把「弹窗」换成「入参从哪来」。

真正的转折来自一处此前未被解释的观测：`#7` 实测到弹窗在 `host → key.steamofl.com:443` 连接建立后 **94 毫秒**出现。这条时序与静态结构互为反面——`_check_cached_verification` 命中时直接进入 `_continue_initialization` 与 `_preload_memory_images`，而 `_fetch_verification_config` / `_handle_verification_config_ready` / `_handle_verification_config_failed` 三者属于**另一条分支**。

**有连接才有弹窗，则无连接即无弹窗。** 而「无连接」所需的，只是一张真实有效的票据。

## Solution

使用样本自身的正常链路取得一张合法票据，使其在缓存命中路径上启动。

操作上是三件事：提交一次当日验证码（手工在弹窗里输入），让样本自己完成「服务端换票 → 落盘缓存」，然后**再启动一次**并观测结果。预期第二次启动命中缓存，不联网、不弹窗。

**本方案不改动 `main.dll`、`KeySteam.exe`、`verification.cache` 的任何字节**，不注入、不挂钩、不打补丁、不构造宿主。所有动作都走样本自己的公开功能。因此完整性自检、运行时守卫、远程清单三条防线都不构成威胁——没有任何东西被改动。

这正是 ADR 0001 的决策内容，本 spec 是它的落地形式。

## User Stories

1. 作为操作者，我希望在样本启动前先完成数据目录与 Steam 插件目录的备份，以便失败时零成本回滚。
2. 作为操作者，我希望在启动任何东西之前先检查是否存在残留的宿主进程，以便不会在未察觉的旧进程上做观测。
3. 作为操作者，我希望监控脚本在样本启动**之前**就已运行，以便即使运行结果很糟，它也是被观测到的。
4. 作为操作者，我希望把当前 `verification.cache` 的存在状态与哈希记录下来，以便事后能区分「首次写入」与「未改动」。
5. 作为操作者，我希望在弹窗里手工输入当日验证码，以便走样本自己的换票链路，而不去复现它的编码。
6. 作为操作者，我希望确认提交后样本确实向 `key.steamofl.com` 发起了连接，以便知道换票这一步真的被执行了。
7. 作为操作者，我希望确认提交后 `verification.cache` 被写入或改写，以便知道票据确实落盘了，而不是只停留在内存里。
8. 作为操作者，我希望在提交成功后关闭样本，以便让下一次启动是一次干净的全新启动。
9. 作为操作者，我希望再启动一次样本，并观测**这次**是否出现 `VerificationDialog`，以便这是由实测回答而不是由推断回答。
10. 作为操作者，我希望观测第二次启动是否仍向 `key.steamofl.com` 发起连接，以便判断缓存命中路径是否真的不联网。
11. 作为操作者，我希望拿到窗口的类名与 Enabled 状态而不只是标题，以便区分「弹窗和主窗口同时存在且主窗口被禁用」与「弹窗根本没出现」。
12. 作为操作者，我希望在第二次启动中仍能看到主窗口正常出现，以便确认「不弹窗」不等于「启动失败」。
13. 作为操作者，我希望确认首次运行的致谢对话框行为未变，以便确认本方案没有影响样本的其他对话框。
14. 作为操作者，我希望确认 `TamperWarningDialog`（「倒卖可耻」）没有出现，以便确认完整性路径没有被扰动。
15. 作为操作者，我希望确认样本没有清理 `config/stplug-in/` 下的 `.lua` / `.ks`，以便知道这次运行没有触发它的破坏性行为。
16. 作为操作者，我希望确认主号目录 `userdata\<main-id>` 未被写入，以便主号保护这条既有结论继续有实测支撑。
17. 作为操作者，我希望用一种不依赖 GUI 的方式判断「缓存命中是否发生」，以便两次观测能互相独立验证。
18. 作为操作者，我希望记录两次启动的完整时间线与原始日志，以便结果可重放而不是靠复述。
19. 作为操作者，我希望把「缓存命中但不弹窗」与「缓存未命中但也没弹窗」区分开，以便不把巧合当成机制生效。
20. 作为操作者，我希望知道票据的实际有效期，以便判断这个方案多久需要重做一次。
21. 作为操作者，我希望知道 `published_at` 的服务端轮换是否会让一张尚未过期的票据失效，以便知道周期性成本到底有多大。
22. 作为操作者，我希望在方案不成立时明确知道它不成立，以便及时止损而不是反复重试。
23. 作为操作者，我希望把样本自己的报错信息（若有）完整保留，以便失败时能定位到具体是哪一环。
24. 作为操作者，我希望验证过程全部只读，以便观测本身不引入新的变量。
25. 作为操作者，我希望这套步骤是可重放的，以便在票据过期后按同样流程再走一次。

## Implementation Decisions

**范围：零字节改动。** 本 spec 不要求对 `main.dll`、`KeySteam.exe`、`verification.cache` 或任何样本文件做写操作。这不是保守，而是与已确证事实一致：票据是签过名的密文块（per-ticket X25519 ECDH），任何本地伪造都不成立，因而「不改动」既是底线也是唯一可行解。

**单一接缝。** 本路线的失败点是单一的：票据是否在缓存命中路径上被接受。因此只设一个接缝——**启动样本，观测窗口集合与网络连接**。宿主/argv 接缝随 ADR 0001 备选 A 的否决一并取消，不再需要。

**验证码的提交入口：手工输入。** 脚本化提交需要复现 `_validate_encrypted_code` 的「明文 → 加密 → KSP1」编码，而该编码的段落边界尚未定位。在未确证的机制上建自动化，会把一个新变量引入一个已经足够清晰的验证里。本轮明确不做自动化。

**复用现有监控脚本，不新建。** `scripts/monitor_keysteam.ps1` 已具备本接缝所需的全部观测能力：`user32 EnumWindows` 全顶层窗口枚举（输出 pid / hwnd / visible / enabled / class / title）、对目标 IP 的 TCP 连接状态、命名管道枚举、数据目录与 stub 目录的实时变化、主号目录写入监控。它已修掉「`Get-Process | MainWindowTitle` 每进程只报一个窗口、会漏掉同进程内模态对话框」这个实测缺陷。给它加一个 `-WatchHost` 之类的开关或另写包装，属于实现自由度；**观测项本身不需要扩充**。

**观测必须以窗口的 enabled 字段为准，不以标题为准。** 弹窗的判据是「`KeySteam v2.99` 主窗口 Enabled=False，同时存在另一个同进程的模态窗口」这一对。只看标题会把「弹窗没出现」与「弹窗出现了但没采到」混为一谈——这正是本项目已登记的错误模式之一。

**失败分支不写进本 spec。** 若实测显示缓存命中仍弹窗（即 `published_at` 轮换让未过期票据失效），本 spec 不预先规定降级方案。那是一个独立的、需要事实支撑的新决策，届时另开票。

**前置条件（硬性）：**
1. 备份 `%APPDATA%\Shikieiki\`（含 `verification.cache` 与 `first_run.cache`）与 `config/stplug-in/` 到 `_re/backup/` 下的新目录，并记录哈希。
2. 运行前检查 `Get-Process host` 及样本进程是否有残留。宿主进程不会被外层 `timeout` 杀掉，这一条是已登记教训。
3. 监控脚本先于样本启动。
4. 不得把宿主或样本包在 `timeout` 里运行。

**术语一律使用 `CONTEXT.md` 的定义。** 特别是：验证码 / 票据（KV1） / AppTicket 三者分属不同发放方，弹窗是「验证码弹窗」而非「倒卖可耻」。

## Testing Decisions

**什么算好测试**：只观测**外部行为**——进程表、窗口集合及其 enabled 状态、TCP 连接、命名管道、文件哈希与 mtime、样本自身的 stdout/stderr 与退出码。不做任何注入、挂钩或补丁。每条断言都是对运行中系统的只读观测，因此**阴性结果可信，重复成本极低**。断言不得依赖样本内部状态，也不得依赖「没有看到就等于不存在」这种推论——凡是否定结论，必须伴随观测手段本身的成功执行证据。

**被测对象**：样本自身作为一个黑盒，通过其正常入口（`KeySteam.exe`）启动两次。不测我们的任何新代码，因为本方案不新增代码。

**接缝（唯一）**：
- 第一次启动：样本出现 → 弹窗出现 → 手工提交当日验证码 → 观测到对 `key.steamofl.com` 的连接 → 观测到 `verification.cache` 被写入或改写 → 正常关闭样本。
- 第二次启动：样本出现 → **观测窗口集合**：是否同时存在模态窗口与 Enabled=False 的主窗口？→ 观测是否仍有到 `key.steamofl.com` 的连接 → 观测 `config/stplug-in/` 与主号目录是否被改动。
- 判定「命中」的正面证据是：第二次启动**没有**可归因到验证的 TCP 连接，**且**主窗口 Enabled=True 且无同进程模态窗口。

**反面证据同样必须采集**：样本无窗口出现、进程立即退出、或出现 `TamperWarningDialog`，都是独立结论，不能被读成「弹窗没出现所以成功了」。

**先例（prior art）**：`scripts/monitor_keysteam.ps1` 本身就是先例，且为上一轮同一目的而写、已修过一轮实测缺陷。运行记录格式参照 `.scratch/run-20260915-125400/`（含 `findings.md` 与原始日志）。

**观测窗口时长**：不短于 60 秒，且以「弹窗是否出现过」而不是「采样瞬间是否有弹窗」为判据——`#7` 的因果链显示弹窗在连接后 94ms 出现，采样慢会直接漏掉。

## Out of Scope

- 伪造、编辑、重签 `verification.cache`；构造宿主；注入或挂钩校验逻辑。
- 绕过 GUI 调用 `AuthorizationWorkflowService` 的 CLI 入口。该入口的入参是 Steam 签发的 Encrypted AppTicket，与号商票据无关，不解决本问题。
- 寻找「不靠票据产出授权产物」的模块。已确证不存在：测试内核仍需 `require_encrypted_ticket`，`KERNEL_NONE` 的 `uses_ticket_authorization=false` 语义是「不做运行时替换」。
- 持久化每日验证码本身以供跨日复用。验证码绑当日，服务端轮换 `published_at`，跨日必被拒。
- 明文验证码到 `KSP1` 提交格式的编码复现（本轮的提交走手工）。
- 远程清单分支（`version.json`）是否参与闸门放行——这是既有开放问题 `#6` 的范围。
- 被取代的「消除弹窗」路线的全部内容。
- `published_at` 轮换导致缓存失效时的降级方案（若实测触发，另开票）。

## Further Notes

**关于本 spec 取代的内容**：`docs/bypass-gui-entrypoints.md` 的 §6 曾建议「用 payload 目录验证 argv 分发可达性」作为下一步。该建议已被 ADR 0001 的备选 A 否决结论覆盖——CLI 入口的入参不是号商票据，走通它也不达成用户目标。该文档 §2 中「取决于 onefile 参数透传行为」的措辞现已知为 DLL 模式（argv 指针直传），属文档一致性收尾，不阻塞本 spec。

**关于周期性成本**：票据带 `expires_at`，服务端还轮换 `published_at`。因此本方案**预期需要定期重做**。`expires_at` 的实际时长**无任何证据**——此前「两天缓存」的推断已被撤回（见 `docs/agents/domain.md` 的 drift 表），当前视为不受控变量。第一次实测应当顺手记录两次启动之间的时间间隔与结果，为这个变量积累第一个数据点。

**关于本机的非隔离状态**：本机已在运行同类工具（`KeySteamTool.dll`、`cloud_redirect.dll`、被替换过的 `steam.exe`）。因此「观测到的现象是否由本样本引起」需要连接与时间线的关联，不能只凭现象出现就归因。

**关于结果报告方式**：先报原始测量，再给解释。本项目已多次出现「看到部分信息就补全成结论」这一错误模式（drift 表中有多条），而本 spec 的阳性判据是一个**否定式观测**（没有弹窗），恰恰是最容易被误读的一类。
