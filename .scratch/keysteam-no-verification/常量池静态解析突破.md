## 1. 推翻既有结论：常量池可静态解析

既有记载（`最快路径研究.md` §3「方法论结论」）：**「静态字符串搜索对 Nuitka 池常量必然失败……必须走行为定位或运行期。」**

**需要限定范围**：
- **成立的部分**：在 `.text` 指令操作数里搜池字符串确实失败（Nuitka 经槽表间接索引，`createModuleConstants` 批量 memcpy 到 BSS）。
- **不成立的部分**：**blob 本体的结构化解析完全可行**。常量池是磁盘上的结构化数据，按官方格式逐字节解析即可。

### 2.1 公式（确证）

常量 32–35 序列 `3a 6e 6c 20 6e` = `SLICE` + `NONE` + `LONG_POS_SMALL 32` + `NONE` → **`[None:32:None]` 即 `[:32]`**。

```python
def _hash_machine_parts(parts):
    return hashlib.sha256(
        "|".join(str(p) for p in parts).encode("utf-8")
    ).hexdigest()[:32]
```

**注意**：是 **`hexdigest`**（常量 31），不是 `digest`。这一点此前记载有误。

### 2.2 4 元组的元素（确证）

```python
parts = [
    _read_windows_machine_guid(),   # HKLM\SOFTWARE\Microsoft\Cryptography\MachineGuid，.strip()
    int(uuid.getnode()),            # 常量 18-22：socket.gethostname / uuid.getnode
    platform.system(),              # 常量 0-1；casefold 用于 == 'windows' 比较
    socket.gethostname(),
]
```

**待确证**：`uuid.getnode()` 是否被 `int()` 包裹（常量表未见 `int` 属性名，故**倾向未包裹**，即直接用 `getnode()` 返回值）；`win_guid` 读取失败时是否回退为常量 25 的 `'unknown-machine'`。

## 3. 推翻切分假设：`KSTK\x01` 是 5 字节

### 3.1 票据模块常量区（偏移 `0x1cd45f0`–`0x1cd4a70`）解码

**magic 三件套**（`0x1cd4a14`）：
```
63 4b 53 56 43 01 00  →  'c'(BYTES_ZERO_TERMINATED) + b"KSVC\x01"
63 4b 53 54 4b 01 00  →  'c' + b"KSTK\x01"
63 4b 53 46 52 01 00  →  'c' + b"KSFR\x01"
```
⇒ **magic 含版本字节 `\x01`，是 5 字节而非 4 字节。**

**`_NONCE_SIZE`**（`0x1cd4a4c`）：
```
6c 0c  →  'l'(LONG_POSITIVE_SMALL) + 0x0c = 12
```
⇒ **`_NONCE_SIZE = 12`**（与 GCM/ChaCha20 标准 nonce 一致）。

**密钥前缀有两个**（`0x1cd4698`、`0x1cd46b8`）：
```
u"KeySteam verification cache v1"
u"KeySteam verification cache v1|"
```
对应两个函数：`a_cache_key` 与 `a_legacy_cache_key`（后者配 `get_legacy_machine_id`）。

**加密算法确证** `aAESGCM`（`0x1cd4724`）+ `u cryptography.hazmat.primitives.ciphers.aead`。
**关键变量名**：`anonce` / `aciphertext` / `amagic` / `astartswith` / `adecrypt` / `aInvalidTag`。

### 3.2 活票据实测切分

文件：`/mnt/d/ks_probe/_bk/verification.cache.live`（sha256 `b044406c31e0afbb1513e471b3675fd18f9ba78b437428983bb1d289a6d17629`）

```
00000000: 4b53 544b 01c5 7556 ce8a c037 bc88 88e8  KSTK..uV...7....
00000010: ff79 b57a 523c 6346 e160 cc48 f0de 5bd2  .y.zR<cF.`.H..[.
```

| 段 | 偏移 | 长度 |
| --- | --- | --- |
| magic | `[0:5]` | 5（`KSTK\x01`） |
| nonce | `[5:17]` | 12 |
| ct+tag | `[17:605]` | **588** |

**旧假设 `4 + 12 + 589 = 605` 是错的**——把 `\x01` 算进了 nonce 区，导致 nonce 变成 `01c57556ce8ac037bc8888e8`（错位）、密文变 589。**差 1 字节的偏移会让所有密钥爆破以「InvalidTag」失败，与「密钥错」不可区分。**

这正是研究子代理标记的**最高系统性风险**，且已在真实数据上确证并修正。

## 4. 已执行的验证与结果

在 WSL 下用**修正后的切分** + **确证公式**跑了 1536 组（4 种 guid 形态 × 2 种 node × 4 种 system name × 3 种 host × 回退组合 × 顺序 × 2 前缀 × 2 分隔 × 2 种 nonce 位置 × 5 种 AAD）：

**全部失败（0 命中）**。

**但不构成公式的否证**——原因明确：`platform.system()` 必须在**样本进程**（Windows）里求值，WSL 的 Python 返回 `'Linux'`；`win_guid` 的读取路径（`winreg`）在 WSL 下也只有经 `reg.exe` 间接取得的值，`.strip()` 与类型转换未确证。

### 4.1 已算出的可验证候选

```
parts = ['e1829dc2-9c30-4c55-8988-f1375d8dc559', 128519045806516, 'Windows', 'DESKTOP-FQI0FAF']
joined = 'e1829dc2-9c30-4c55-8988-f1375d8dc559|128519045806516|Windows|DESKTOP-FQI0FAF'
```

**这给出 kd4 的最终判据**：`key_dump.py` 从 `[r8]` 解出的元组，拼出的字符串**应当精确等于上面这行 `joined`**（或 `'Linux'` 变体 `3ad71053ee6e0087cd56f6ead5f8b0de`）。若不等于，说明 `parts` 的构成仍有未知。

## 5. 对本项目的可操作结论

1. **静态侧已无阻塞项**。`machine_id` 公式、`_NONCE_SIZE`、magic 长度、分隔符、加密算法全部确定。
2. **下一步唯一要做的是运行期取值**，且**判据已精确化**：不再需要「探索性 dump」，而是**比对一个已知目标字符串**。`key_dump.py` 的 kd4 已含 `r8->[0]` 候选，正是读该元组。
3. **此前的 2 万组爆破结论需重估**：它们基于错误的切分（`4+12+589`），**否定结果不成立**。
4. **`unknown-machine` 回退**是一个此前未覆盖的维度。
5. **`hexdigest` vs `digest`**：`_hash_machine_parts` 用 `hexdigest()[:32]`；票据模块的 `_cache_key` 常量区见 `adigest`（非 `ahexdigest`），两者**可能不同**，需分模块确证。
