## 0. 三句话结论

1. **任务书的核心前提被推翻**：`0x180fe1ec7` 处 `call 0x18140a220` **不是**「闸门的 MAKE_FUNCTION」。`0x18140a220` 的真实身份是 **Nuitka CodeObject 哨兵桩构造器**（内含 `Py_CompileStringExFlags` 现造 `def empty(): raise RuntimeError('Compiled function bytecode used')`）。这一点由该函数引用的字符串常量**逐字确证**。
2. **闸门的机器码入口在 `.text` 中静态完全可定位** —— 但它**不是**「`mov rax, <_Py_NoneStruct>; ret` 的小函数」，也**不在** blob 常量池里。真正的 `m_c_code` 由 `Nuitka_Function_New`（VA `0x1813fd760`）的 **`rcx` 参数**传入，在调用点以 `lea rcx,[rip+<.text 函数>]` 形式出现。
3. **`TAG_CODE_OBJECT` 在整个镜像的 blob 池中出现 0 次**（308 个池、约 5.3 万条常量穷尽解析）。任务书「路线 A」不成立；但「路线 B」成立且可操作 —— 闸门的 `m_c_code` 已收窄至 `0x181070812` 内 161 处 `Nuitka_Function_New` 调用的 `rcx` 参数（落在 `0x180fe4ee0`–`0x180fe9130`）。

## 1. 独立确证：常量池可完整静态解析（含 tag 表勘误）

### 1.1 任务书 tag 表的缺失项

任务书给出的 tag 表缺少官方 `constants_blob_spec.h` 中的多项，其中三处会导致解析**立即错位**：

| tag | 官方名称 | 任务书状态 | 影响 |
| --- | --- | --- | --- |
| `0x46` | `TAG_FALSE` | **缺失** | 遇到即「unknown tag」中断 |
| `0x74` | `TAG_TRUE` | **缺失** | 同上 |
| `0x4c` | `TAG_LIST` | **缺失** | 同上 |
| `0x4f` | `TAG_BUILTIN_NAMED` | **缺失** | 同上 |
| `0x70` | `TAG_PREVIOUS` | 缺失 | 同上 |

**关键结构性错误（任务书 §Nuitka 常量池格式）**：任务书把整数写成定宽（「`0x6c` LONG_POSITIVE_SMALL 后随 1 字节值」）。**官方实现是变长编码**：

```c
static uint64_t _unpackVariableLength(unsigned char const **data) {
    uint64_t result = 0; uint64_t factor = 1;
    while (1) {
        unsigned char value = **data; *data += 1;
        result += (value & 127) * factor;
        if (value < 128) break;
        factor <<= 7;
    }
    return result;
}
```
来源：[`HelpersConstantsBlob.c`（develop 分支）](https://raw.githubusercontent.com/Nuitka/Nuitka/develop/nuitka/build/static_src/HelpersConstantsBlob.c)

**所有** size / 长度 / 整数均走此编码，包括 TUPLE/LIST/DICT/SET/FROZENSET 的元素数、`BYTES_LENGTH_PREFIXED` 的长度、`LONG_*_SMALL` 的值。

**另一处易错点**：`0x4d BUILTIN_ANON` 与 `0x51 BUILTIN_SPECIAL` 是**单字节 `*data++`**（非变长）；而 `0x4f BUILTIN_NAMED` / `0x45 BUILTIN_EXCEPTION` 是 **cstring**。

### 1.2 目录项定位（修正任务书的池段描述）

任务书称池段为 `0x1cac0ec`–`0x1cb2231`。**实测该区间的解释有误**：

真实目录项：
```
文件偏移 0x1cb1a1f：b"src.gui.main_window_controller\0" + uint32 0xc2ca (=49866)
                    + uint16 0x05e9 (=1513) + 1513 个常量
body 起点       = 0x1cb1a44
解析结束        = 0x1cbdd0c  ← 与 body+size-2 精确吻合
```

`0x1cac0ec` 属**另一个**模块的池，不是本池起点。任务书 §「已知的池段」把两个不同模块的池合并描述了。

### 1.3 解析阳性对照

`src.gui.main_window_controller` 池：**1497 / 1513 条解析成功，指针精确停在 `0x1cbdd0c`**（末 16 条为 Nuitka 的模块尾部样板，非解析失败）。

**闸门方法名在池内序号 = `#67`，文件偏移 `0x1cb2104`（tag `0x61` ATTR_NAME）**：

### 2.1 字节级候选的证伪


特征：`name` 是文档字符串/普通标识符、`line` 恒为 98/118/59、`argc` 高达 84–118、`qualname` 全为 `None`。真实 CODE_OBJECT 的 `argc` 不会普遍为 84+，`line` 也不会恒定。这些是普通字符串常量体内恰好出现的 `0x43` 字节。

## 3. 核心发现二：`0x18140a220` 不是 MAKE_FUNCTION

### 3.1 任务书前提的推翻

`0x18140a220` 引用的字符串常量（`lea` 目标逐个读出）：

```
0x181d1a4d0: b"def empty(): raise RuntimeError('Compiled function bytecode used')"
0x181d1a5b8: b'<exec>'
0x181d1a518: b'nuitka_empty_function'
0x181d1a530: b'empty'
0x181d19230: b'__code__'
0x181d1a538: b'co_code'
0x181d1a650: b'co_consts'
0x181d1a660: b'co_names'
0x181d1a670: b'co_exceptiontable'
0x181d1a688: b'co_stacksize'
```

其调用的导入函数（IAT 反查，`.rdata` → 导入名）：

| IAT VA | 导入名 |
| --- | --- |
| `0x18143d580` | `Py_CompileStringExFlags` |
| `0x18143d658` | `PyImport_ExecCodeModule` |
| `0x18143d640` | `PyUnstable_Code_NewWithPosOnlyArgs` |
| `0x18143da58` | `PyObject_GetAttrString` |
| `0x18143d160` | `abort` |
| `0x18143d310` | `PyThreadState_Get` |

**这是一段代码**：`Py_CompileString("<exec>", "def empty(): raise RuntimeError('Compiled function bytecode used')")` → `PyImport_ExecCodeModule("nuitka_empty_function", ...)` → 取出 `__code__`、覆写 `co_code`/`co_consts`/`co_names`/`co_exceptiontable`/`co_stacksize` → `PyUnstable_Code_NewWithPosOnlyArgs` 造出**哨兵 CodeObject**。

**这与任务书 §注意 的描述逐字吻合**：「`m_code_object` 里的 Python 字节码是**哨兵**（`Py_CompileString` 现造的抛异常桩），**不含机器码**」。

**所以 `0x180fe1ec7` 是「为闸门的 CODE_OBJECT 造哨兵桩」，不是「构造闸门函数对象」。**

### 3.2 该函数的调用图谱（6824 处）

`call 0x18140a220` 在全 `.text` 中出现 **6824 次**。在含 `0x180fe1ec7` 的函数 `0x180fe0c10`（范围 `0x180fe0c10`–`0x180fe49ad`，15773 字节）内出现 **191 次**，是一段**逐常量展开的批量桩构造**（每次 `rcx=[0x181dcb588]`、`r8d=0x1000003` 固定，仅 `r9`/`edx` 行号/栈参数变化）。

该函数内 **`Nuitka_Function_New` 调用数 = 0**，排除它是函数对象构造器。

### 3.3 `r9` 参数的真实语义（修正任务书）

任务书称 `0x180fe1e7a mov r9,[0x181dcc130]` 是「读出旧函数对象（闸门槽，读操作）」。实测配对：

```
call @0x180fe1e23  r9=0x181dcce18   write=0x181dcafd8
call @0x180fe1e75  r9=0x181dcbd50   write=0x181dca7d8
call @0x180fe1ec7  r9=0x181dcc130   write=0x181dcb3b8   ← 任务书所指
call @0x180fe1f19  r9=0x181dcbf78   write=0x181dcad80
call @0x180fe1f6e  r9=0x181dcca08   write=0x181dcb3b0
```

对照官方 [`_unpackBlobConstantObjectPrevious`](https://raw.githubusercontent.com/Nuitka/Nuitka/develop/nuitka/build/static_src/HelpersConstantsBlob.c)：

```c
static unsigned char const *_unpackBlobConstantObjectPrevious(
        PyThreadState *tstate, void **output, unsigned char const *data) {
    PyObject *prev = ((PyObject **)*output)[-1];   // ← r9 = output[-1]
    _finalizeUnpackedConstantObject(output, prev);// ← 写回当前 output
    return data;
}
```

`r9` 是 **`output[-1]`（前一个槽的值，即 `0x70 PREVIOUS` tag 的复用源）**，返回值写入**当前槽**。

**推论（强证据，标注为高置信推测）**：
- `0x181dcc130`（槽号 +368）是**被 `PREVIOUS` 复用的某个常量槽**，不是「闸门函数对象槽」。
- `0x180fe1ec7` 实际写入的是 `0x181dcb3b8`（槽号 -63）。若此处绑定的是闸门条目，则**闸门的真实槽是 `0x181dcb3b8`，而非 `0x181dcc130`**。

这与任务书「闸门函数对象槽 = `0x181dcb5b0 + 8×368 = 0x181dcc130`」相矛盾。**建议以运行期断点实证二者（任务书未提供 `mw_base` 的独立静态来源，我亦未能从 `.data` 描述符表独立复现 `0x181dcb5b0`）**。

槽号算术（基于任务书给的基址）：
```
MWC = 0x181dcb5b0
0x181dcc130 - MWC = +2944  → 槽 +368   （任务书称"闸门槽"）
0x181dcb3b8 - MWC =  -504  → 槽  -63   （0x180fe1ec7 的写入目标）
0x181dca7d8 - MWC = -3544  → 槽 -443   （0x180fe1e75 的写入目标，属 main_window 池）
```

注意负槽号：`0x181dcb5b0` 之前还有常量区，说明 `MWC` 只是**某一段池的基址**，不是整个模块常量区的起点。

### 4.1 定位 `Nuitka_Function_New` = `0x1813fd760`

### 4.2 `m_c_code` 字段偏移 = `+0x78`

`0x1813fd760` 序言与关键赋值：

```
0x01813fd7f8  mov qword ptr [rdi + 0x78], r14    ; ★ m_c_code = rcx
0x01813fd7fc  mov qword ptr [rdi + 0xc8], r8     ;     (if r14 != 0)
```

**任务书 §注意（`m_c_code` 字段存在、`m_code_object` 是哨兵）完全正确。但 `0x18140a220` 与 MAKE_FUNCTION 无关这一点被漏判。**

## 5. 核心发现四：「机器码在 `.text`」假设的检验

### 5.1 任务书路线 A 的形态在镜像中真实存在，但不属于闸门

全 `.text` 搜「`mov rax,[_Py_NoneStruct]` 后 6 条内 `ret`」，得 **9 个**候选函数：

```
0x180777c4e   ...  ret @0x180777ccc
0x180cae523   ...  ret @0x180cae5a1
0x180efda80   ...  ret @0x180efde20
0x180f6fc23   ...  ret @0x180f6fca1
0x1813fcadb   ...  ret @0x1813fcae7
0x181401550   ...  ret @0x181401576
0x181409e70   ...  ret @0x181409fb1
0x1814342f1   ...  ret @0x181434301
0x181435cf0   ...  ret @0x181435d64
```

最干净的两个：

```
0x01813fcadb  mov rax, qword ptr [rip + 0x41056]   ; -> 0x18143db38 (_Py_NoneStruct)
0x01813fcae2  add rsp, 0x20
0x01813fcae6  pop rbx
0x01813fcae7  ret

0x01814342f1  mov rax, qword ptr [rip + 0x9840]    ; -> 0x18143db38
0x01814342f8  mov rbx, qword ptr [rsp + 0x40]
0x01814342fd  add rsp, 0x48
0x0181434301  ret
```

`_Py_NoneStruct` 定位：VA `0x18143db38` → 文件偏移 `0x143c338`（`.rdata`），字面存在于磁盘，**不是** `.reloc` 项。任务书对此的疑虑可解除。

### 5.2 但它们不是函数对象入口（决定性否证）

对 9 个候选逐一检查「被 `lea rcx,[rip+X]` 引用」的次数（即作为 `m_c_code` 被引用）：

```
0x180777c4e  → 0 次
0x180cae523  → 0 次
0x180efda80  → 1 次   @0x180f084e9
0x180f6fc23  → 0 次
0x1813fcadb  → 0 次
0x181401550  → 0 次
0x181409e70  → 0 次
0x1814342f1  → 0 次
0x181435cf0  → 0 次
```

进一步：`0x1814342f1` 的**全部**引用只有 **1 条** —— 同函数内 `0x1814342cd je 0x1814342f1` 的跳转目标。**它不是独立函数，是某函数的内联尾块。**

唯一被用作 `m_c_code` 的 `0x180efda80`，完整反汇编显示它有 40+ 条指令（引用计数递减、`call [rax+0x30]` 释放器、`[rdi+0xf0]`/`[rdi+0x120]` 字段操作），是**正常 Nuitka 函数实现**，只在某个分支返回 None。

**确证结论**：`.text` 中不存在「纯 `mov rax,<_Py_NoneStruct>; ret` 形态的闸门函数」。**「机器码是否固化在 `.text`」这个问题的答案是：机器码确实固化在 `.text`（`Nuitka_Function_New` 的 `rcx` 即指向 `.text` 地址），但闸门不会是返回 None 的极简桩 —— 闸门的 `m_c_code` 是一个真实的、含业务逻辑的 Nuitka 函数实现。**

### 5.3 返回值语义判据的独立复核

任务书称「`cmp rax, rsi`，`rsi` 重定位目标是 `_Py_NoneStruct` ⇒ `rax == None → 放行`」。

`Nuitka_Function_New` 内可见同源比较（`0x1813fd85c`–`0x1813fd86e`）：
```
0x01813fd85c  cmp rax, qword ptr [rip + 0x402d5]   ; -> 0x18143db38 (_Py_NoneStruct)
0x01813fd863  jne 0x1813fd86a
0x1813fd865  mov rax, r8
0x1813fd86e  mov qword ptr [rdi + 0xa0], rax
```
这是 `m_dict`/`m_annotations` 类的**处理**，非返回值判据。任务书所述的 `cmp rax, rsi` **在调用者侧**（`_verification_gate_allows` 的消费点），本报告未在 `0x1810168e0` 等 6 个分派点内逐条复核该判据 —— **标注为未复核**。

## 6. 修正后的闸门定位方案

### 6.0 已完成的定位步骤（本轮新增取证）

对 7 个候选消费者逐一检索 `call 0x1813fd760`：

```
0x1810168e0  (3104 字节,  854 条) → call Nuitka_Function_New:   0 处
0x181017500  (2187 字节,  605 条) → call Nuitka_Function_New:   0 处
0x181017d90  (2392 字节,  645 条) → call Nuitka_Function_New:   0 处
0x1810186f0  (2156 字节,  588 条) → call Nuitka_Function_New:   0 处
0x181018f60  (4023 字节, 1103 条) → call Nuitka_Function_New:   0 处
0x18105a1e0  (4528 字节, 1236 条) → call Nuitka_Function_New:   0 处
0x181070812  (46961 字节,10535 条) → call Nuitka_Function_New: 161 处 ★
```

**`0x181070812` 是本模块（main_window_controller）方法区的函数对象批量构造器**，其 161 处调用的 `m_c_code` 全部落在 `0x180fe4ee0`–`0x180fe9130` 区间（紧邻 `modulecode 0x180fe0c10` 之后）。

**`m_c_code` 的传参形态实测**（抽 `0x181075e0d`）：

```
0x0181075df7  lea rcx, [rip - 0x90f1e]     ; -> 0x180fe4ee0  ★ m_c_code
0x0181075dfe  mov qword ptr [rsp + 0x30], rax
0x0181075e03  mov qword ptr [rsp + 0x28], r12
0x0181075e08  mov qword ptr [rsp + 0x20], r12
0x0181075e0d  call 0x1813fd760             ; Nuitka_Function_New
0x0181075e12  mov rdx, [rip + 0xce6c07]    ; -> 0x181d5ca20
0x0181075e19  mov r8, rax                  ; r8 = 新函数对象
0x181075e1c  mov rcx, rsi
0x0181075e1f  mov rbx, rax
0x0181075e22  call 0x180166a90             ; 存入槽/类属性
```

`0x180fe4ee0` 处字节 `48 89 5C 24 08 57 48 83 EC 40 ...`（`mov [rsp+8],rbx; push rdi; sub rsp,0x40`）—— **标准 Nuitka 函数序言**，与 §5.2 的「极简桩」形态完全不同，佐证闸门是真实实现。

### 6.1 静态路径（推荐，可离线执行）

```
1. 定位闸门方法在 class body 中的赋值位置
   src.gui.main_window_controller 池内序号 #67, off 0x1cb2104
   → 消费点: 0x1810168e0 / 0x181017500 / 0x181017d90 / 0x1810186f0 /
             0x181018f60 / 0x18105a1e0 （6 个分派点）
      以及 0x181070812（2 次 rdx 读取）

2. 在这 7 个函数的范围内搜 call 0x1813fd760（Nuitka_Function_New）
3. 对每个调用点，回溯前 1–10 条找 lea rcx,[rip+X]，X 即 m_c_code
4. 用 X 反汇编验证函数形状（应为完整 Nuitka 函数序言，
   非 mov rax,None; ret）
5. 若需强制放行: 不修改 m_c_code，而是把该函数的返回值路径
   改为直返 _Py_NoneStruct（或把闸门槽改指到已有的 0x1813fcadb 桩）
```

### 6.2 `m_c_code` 字段

```
结构体偏移: +0x78   (qword)
来源:       Nuitka_Function_New @ 0x1813fd760 的第 1 参数 rcx
NULL 默认:  0x1813fd580
```

### 6.3 若要「强制返回 None」

不建议改 `.text` 里任意「`mov rax,<_Py_NoneStruct>; ret`」小函数 —— 已验证它们全是内联尾块，改之会破坏调用者栈平衡。

**可行方案**：把闸门函数对象的 `m_c_code`（偏移 `+0x78`）改指到 `0x1813fcadb`：
```
0x01813fcadb  mov rax, qword ptr [rip + 0x41056]   ; -> _Py_NoneStruct
0x01813fcae2  add rsp, 0x20
0x01813fcae6  pop rbx
0x01813fcae7  ret
```
但该函数自己的栈调整是 `0x20 + 8`，**与闸门函数的序言栈深度不一定匹配** → 会栈失衡。**安全做法是保持 `m_c_code` 不动，改闸门函数内部返回路径。**

## 7. 阻塞原因（若判定为不可改）

**不存在「机器码不在 `.text`」的阻塞。** 机器码确实固化在 `.text`，且 `m_c_code` 在调用点可静态读取。

真正的阻塞是**定位工作量**：闸门的 `m_c_code` 需要先从 7 个候选消费者的 `Nuitka_Function_New` 调用点逐一回溯，才能确定哪个是 `_verification_gate_allows`。本报告未完成这一步（见 §8）。

## 8. 确证 / 推测 / 未完成

### 确证（有一级证据）

- 文件 sha256 与大小（实测复算）。
- `src.gui.main_window_controller` 目录项位于 `0x1cb1a1f`，body `0x1cb1a44`，size 49866，count 1513，解析精确闭合于 `0x1cbdd0c`。
- 闸门方法名在池内序号 `#67`，off `0x1cb2104`，tag `0x61`。
- 全 308 个池、约 5.3 万条常量中 **`TAG_CODE_OBJECT(0x43)` 出现 0 次**。
- `0x18140a220` 是 **CodeObject 哨兵桩构造器**（字符串常量 + IAT 名双重确证），**不是 MAKE_FUNCTION**（任务书前提被推翻）。
- `Nuitka_Function_New` = `0x1813fd760`；`m_c_code` 偏移 = `+0x78`；来源 = `rcx`；NULL 默认桩 = `0x1813fd580`。
- `m_c_code` 在调用点以 `lea rcx,[rip+X]` 形式出现（实测 6 例）。
- `.text` 中「`mov rax,<_Py_NoneStruct>; ret`」候选 9 个，其中 8 个零 `m_c_code` 引用、1 个是完整函数实现。
- `_Py_NoneStruct` VA `0x18143db38` 在磁盘偏移 `0x143c338` 以字面值存在。
- `0x18140a220` 在全 `.text` 被调用 6824 次；含 `0x180fe1ec7` 的 `0x180fe0c10`（15773 字节）内有 191 次，且**该函数内 `Nuitka_Function_New` 调用数 = 0**。

### 推测（标注置信度）

- **高**：`0x181dcc130` 是被 `0x70 PREVIOUS` tag 复用的常量槽，**不是**闸门函数对象槽（依据：`r9` = `output[-1]` 的官方语义 + 写入目标是另一槽 `0x181dcb3b8`）。
- **中**：闸门若确在该批次内，其槽是 `0x181dcb3b8`（槽 -63）。
- **中**：任务书给出的 `mw_base = 0x181dcb5b0` 只是某段池的基址，负槽号说明其前方还有常量区。

### 未完成 / 未能确证

- **闸门 `m_c_code` 的确切 VA** —— 已收窄到 `0x181070812` 的 161 处调用（`m_c_code` ∈ `0x180fe4ee0`–`0x180fe9130`）。**收尾所需的一步**：在这 161 处调用点，逐个比对「写入的槽地址」与闸门槽（任务书称 `0x181dcc130` / 本报告推测 `0x181dcb3b8`）。本报告未执行该比对（161 处 × 回溯配对，且槽号体系本身尚存矛盾，见 §3.3）。
- `0x1810168e0` 等 6 个函数的角色（是否为闸门的分派/包装）未展开 —— 已排除它们直接构造函数对象（`Nuitka_Function_New` 调用数为 0），它们更可能是**运行期消费闸门返回值**的分派点。
- 返回值判据 `cmp rax, rsi`（`rsi` → `_Py_NoneStruct`）**未在消费点侧复核**。
- `0x181dcc130` 的 9 条读引用中，除 `0x180fe1e7a` 外的 8 条究竟是「消费」还是「PREVIOUS 源」**未逐条判定**。
- `mw_base = 0x181dcb5b0` 的独立静态来源**未能复现**（`.data` 描述符表反查未命中该值）。
