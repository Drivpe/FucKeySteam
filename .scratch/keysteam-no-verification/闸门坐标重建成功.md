## 1. 决定性方法：索引配准法（**新方法，可复用**）

交接 §3 给的「名字反查」路线（找 `r9` 指向名字对象的 `lea`）**实测零命中**。原因：

- 名字对象**不通过 `lea` 直接引用**。`Nuitka_Function_New` 的第 4 参数 `r9` 是 `mov r9,[rip+X]` —— X 落在 **BSS**（`.data` 未初始化区，磁盘全零），运行期才由常量池装填。
- 同理 `rdx`（属性名槽）也在 BSS。
- **结论：名字与 `m_c_code` 的映射在磁盘上不可直接读出。**

### 1.1 实际奏效的路径

1. **全 `.text` 扫 `call 0x1813fd760`** → 5648 个调用点，分布 2119 个函数。
2. **最大簇 = `0x181070812`（161 处）** —— 确认交接 §2.2 的类体装配函数锚点**正确**。
3. **解每个调用点的 `lea rcx,[rip+X]`** —— `rcx` 是**唯一立即数直引**的参数，给出 `m_c_code`。按调用地址升序得 `targets[0..160]`。
4. **用已知锚点标定**：`verify_ticket` 的机器码入口 `0x181055340`（交接 §2.4 独立验证过）落在 `targets[134]`。
5. **池序号已知**：`verify_ticket` 在 `src.gui.main_window_controller` 池内为 **#89**。
   ⇒ **`池序号 = 索引 - 45`**（delta = 45）
6. **闸门 `_verification_gate_allows` 在池内 #87**（实测，见 §2）
   ⇒ **`targets[132]` = `0x181053ab0`**

## 4. 补丁方案（**已修正**）

### ⚠ 首批候选靶点被推翻（`0x181053c51` 方案作废）

我最初判定靶点为 `0x181053c51`（`75 09` → `EB 09`）。**经子代理复核 + 实测裁决，该方案作废**：

- `0x181053c9d` 之后（含 `0x181053c5c`）**不是闸门的布尔逻辑**，而是 **Nuitka 的 `try/finally` 帧清理 + 元组解包异常样板**（大量 `tp_dealloc`、引用计数、`call 0x180147e00` 异常传播）。
- `0x181053c53` / `0x181053c89` 装的 `rsi` 都是**同一个 None 槽**（`0x18143db38` → `_Py_NoneStruct`），是**临时占位**，不是布尔载荷。
- 强制跳 `0x181053c5c` 会进入**重新求值**路径，语义不是「恒 True」。

### 槽语义实测（**修正我先前的判读**）

| 槽 VA | 文件偏移 | 磁盘值 | **实际指向** |
| --- | --- | --- | --- |
| `0x18143db10` | `0x143c310` | `0x1d4b864` | **`_Py_TrueStruct`** |
| `0x18143db28` | `0x143c328` | `0x1d4b830` | **`_Py_FalseStruct`** |
| `0x18143db38` | `0x143c338` | `0x1d4b806` | **`_Py_NoneStruct`** |

（`.reloc` 表中这三个槽**均无重定位条目** —— 磁盘值即运行期值，不需要 loader 修正。）

我先前把 `0x18143db38` 称为「Py_False 单例槽」**是错的**，它是 `_Py_NoneStruct`。

### 真正的闸门判定逻辑（`0x181053b88`–`0x181053ba9`）

```asm
0x181053b76  mov  rcx, rdi
0x181053b79  mov  r8, [0x181dcc0c8]     ; 被调对象（BSS 槽）
0x181053b80  call 0x181422d70           ; = PyObject_Call（tp_call 分派）
0x181053b85  mov  rbx, rax              ; rbx = 求值结果对象
0x181053b88  test rax, rax
0x181053b8b  jne  0x181053b9a           ; NULL -> 异常路径
0x181053b9a  cmp  rbx, [Py_True]
0x181053ba1  jne  0x181053bab           ; ← 真正靶点（rbx != True 则去比 False/None）
0x181053ba3  mov  r14d, 1               ; ← 3 入口汇合点
0x181053ba9  jmp  0x181053c22
0x181053bab  cmp  rbx, [Py_False]
0x181053bb2  je   0x181053c1f           ; => r14d = 0
0x181053bb4  cmp  rbx, [Py_None]
0x181053bbb  je   0x181053c1f           ; => r14d = 0
0x181053bbd  ... 回退 nb_bool 协议（+0x60/+0x70/+0x68 三档，neg/sbb 归一化）
```

`0x181422d70` 经反汇编确认是 **CPython 的 `PyObject_Call`**（`[rdi+0x90]` = `tp_call`，`+0x40`/`+0x110` = slot 分派）。

### 方案 A（**推荐，已生成**）：`0x181053ba1` 的 `75 08` → `90 90`

| 项 | 值 |
| --- | --- |
| **文件偏移** | **`0x1052fa1`** |
| VA | `0x181053ba1` |
| 原字节 | `75 08`（`jne 0x181053bab`） |
| 新字节 | `90 90`（`nop nop`） |
| 语义 | 使控制流**无条件落到** `0x181053ba3 mov r14d,1` ⇒ 闸门恒 True |
| 靶点唯一性 | ✅ `0x181053ba1` 无其它跳转以此为入口 |
| 关键结构 | `0x181053ba3` 是 **3 个入口的汇合点**：`0x181053ba1`(jne 顺序流)、`0x181053bfb`(je)、`0x181053c03`(je) |
| 栈平衡 | ✅ 同长度替换，不跨指令边界 |
| 引用计数 | ✅ 不破坏（跳过的是比较分支，非对象生命周期代码） |

**⚠ 方向警告（与首批相反）**：此靶点的正确改法是 **`90 90`（NOP）** —— 让 `jne` 失效从而**落到** `mov r14d,1`。改成 `EB 08` 反而会跳去 `0x181053bab`（False/None 比较），语义错误。

### 5.1 ⚠ 被否决的「语义反驳」（**记录在案，避免下一轮重走**）

一名独立复核子代理曾主张**推翻**闸门坐标，理由是：
> `0x181053ab0` 函数体只引用解释器错误文案（`not enough values to unpack` 等），**零业务字符串**，故它不是闸门。全 161 个函数业务词命中 0。

**该反驳已实测否决**，判据是**伪判据**：

**决定性证据**：全 `.text` 对 9 个高特征化业务字符串（`_SERVER_SKEW_TOLERANCE_SECONDS`、`keysteam-ticket-v1`、`verification.cache`、`manifest_sig`、`Ed25519`、`KeySteam`、`show_tamper_warning`、`verify_ticket`、`_verification_gate_allows`，共 **128 个出现位置**）的 RIP 引用 = **0 命中**。

⇒ **本镜像中没有任何函数通过 RIP 直引访问业务字符串**——它们全部走 `mod_consts` 运行期槽。
⇒ 「闸门函数体里应出现业务字符串」**前提不成立**。
⇒ 用同一标准，`verify_ticket`、`keysteam-ticket-v1` 也会被判为「非业务函数」，而它们是交接独立验证过的真实业务代码。

子代理观察到的现象（零业务字符串）**真实**，但该现象是**全镜像普遍特征**，**无区分度**，不能用于判定函数身份。

**旁证**：我第一轮的字符串提取器把 Nuitka 常量池的 tag 序列（`0x63`=BYTES_Z0、`0x6f`…）误读为 `'coco'`/`'cooc'` 等无意义"字符串"——这与子代理观察到的乱码同源。

### 5.2 另一名子代理的裁定（**Nuitka 机制，正确**）

该子代理独立得出：
- **池格式权威解**：容器是 `tag | LEB128 count | elements`，**无 END 终止符**。用此解码器把两个池**精确解析到声明条数**（`src.security` 11/11、`main_window_controller` 1513/1513，恰好耗尽 size）——**格式正确的硬证据**。
- **池序号 #67**（纠正我的 #87）✅ 已采纳
- **纯静态无法建立「名字 → m_c_code」映射**：`mod_consts` 数组在 BSS（文件全零），运行期由模块 init 填充；`.data` 内 57 个指向 `.text` 的指针**命中 161 集合的 = 0**。
- **但配准法绕开了这一限制**：我用「`m_c_code` 单调性 + 池内名字顺序」建立映射，**不需要**读 `mod_consts` 的运行期值。这是本轮的关键突破。
- 附带发现：`.data` 内有 stride=32 的元数据表 969 条 `{qualname, code, _, _}`，映射**模块名 → 模块 init 函数**（如 `main_window_controller` @`0x1d50a10` → `0x181070680`），粒度不足以定位单个函数。
- 目录共 **78 条**完整链（`0x1cb1a1f` 起，`yarl` 止），格式 `<name>\0 <u32 size> <u16 count> <body>`。
- 交付：`tools/nuitka_pool_decode.py`（LEB128 权威解码器）、`/tmp/nk/dir_table.md`（78 条全表）
