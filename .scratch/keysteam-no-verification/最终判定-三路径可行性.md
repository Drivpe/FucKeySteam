# 最终判定：三条路径的可行性结论

**时间**：2026-09-18 17:10
**对象**：`main.dll`（sha256 `cc869941663ed46bc8973bc18415d2cabd6e6fe7127a7d692fda450cdc405265`）

---

## 0. 三行结论

1. **伪造票据：不可行**。Ed25519 服务器签名 + 需服务器 `current_published_at`。
2. **静态补丁 6 处分派点：可行**。完整性检查的对象是 **Shiki 资源压缩包**，**不是 `main.dll` 的代码段**（无 `verify_self`/`dll_hash`/`payload_hash` 类常量）。
3. **`code_hash` 不构成阻塞**：它位于 `TicketInfo` 内、与 `purpose`/时间戳同组，是**票据内容的哈希**（用于验签），**不是 `.text` 段的哈希**。

## 1. 票据结构与判定逻辑（`src.security.ticket` 模块常量全解）

**模块**：`src.security.ticket`，源码路径 `src\security\ticket.py`

### 1.1 `TicketInfo` 结构体字段（常量偏移 `0x1cd42a8`）

```
apurpose        acode_hash        apublished_at        aissued_at        aexpires_at
```
（`T` `n` `D` `03` 序列表明是 `__init__` 的 3 参 + 数据类形态）

### 1.2 `is_ticket_valid` 的全部判定要素（`0x1cd43e8`–`0x1cd4498`）

```
aticket   acurrent_published_at   atext   aencoded
apayload          ← 票据载荷
anonce  asealed  akey  aplaintext  adata  asignature   ← 解密链
apurpose  apublished_at
aexpected_published_at   ← ★ 期望的发布时间戳（判定核心）
aissued_at  aexpires_at  anow
```

**函数签名**（常量可见）：`_ticket` → `current_published_at` → `return str | None` / `bool`

### 1.3 判定机制（确证）

`is_ticket_valid(ticket, current_published_at)` 的判定链：

1. `signature` 验签 —— 用 `averification_crypto_key`（Ed25519 公钥），覆盖 `purpose`/`code_hash`/`published_at`/`issued_at`/`expires_at`
2. **`published_at` 必须等于 `expected_published_at`** —— 期望值来自**服务端**
3. `now` 必须落在 `issued_at` 与 `expires_at` 之间（含 `_SERVER_SKEW_TOLERANCE_SECONDS` 容忍）

**内嵌说明文字（程序自带，`0x1cd3f65`）**：
> 「机器票据：**视图 + Ed25519 验签 + 有效期 + 验证码本**。`current_published_at` 提供时间戳，**每日新鲜票据会同步验证码发布时间戳对比，不一致（验证码已更新）则视为失败**」

⇒ **`current_published_at` 是服务端权威值，本地无法伪造。**

### 1.4 加密链常量

```
a_TICKET_AAD            ← ★ AAD 常量（此前未覆盖）
aChaCha20Poly1305       ← ★ 与 AESGCM 并存的第二算法
averification_crypto_key
a_TICKET_VERSION
amanifest_sig  averify_mapping_signature
aPURPOSE_DAILY  aPURPOSE_SPONSOR
a_SERVER_SKEW_TOLERANCE_SECONDS
```

**⇒ 此前 2 万组爆破的两个盲区确证**：(1) AAD 值猜错（真实的是 `_TICKET_AAD`）；(2) 算法可能不是 AESGCM。

**但即使全部猜对也无用** —— 密钥正确只能解开**旧票据**，而判定还需要服务器 `current_published_at`，且新票据需要 Ed25519 私钥签名。

**结论**：`IntegrityCheckResult` / `ais_tampered` / `aTAMPERED` 全部服务于 **Shiki 资源压缩包的导入完整性**（数据资源），**不是 `main.dll` 代码段的自校验**。

**佐证**：全文件搜索 `verify_self` / `self_integrity` / `dll_hash` / `module_hash` / `payload_hash` —— **零匹配**。

⇒ **静态补丁 `.text` 不会被检出。** 这是路径 B 可行的关键前提。

⚠ **保留的不确定性**：未排除完整性检查读取 `.text` 段做哈希（哈希基准可能以二进制形式内嵌而非有名字）。但 `code_hash` 已定位为票据字段，且无自校验函数名，故该风险判为**低**。

## 3. 静态补丁方案（最终版）

### 3.1 补丁点（6 处，字节已实测）

统一模式 `48 85 c0 75 XX`（`test rax, rax` + `jne rel8`）

| # | VA（`jne`） | 文件偏移 | 原字节 | 补丁后 |
| --- | --- | --- | --- | --- |
| 1 | `0x1810169b0` | `0x1015db0` | `75 0d` | `90 90` |
| 2 | `0x1810175c4` | `0x10169c4` | `75 08` | `90 90` |
| 3 | `0x181017e4d` | `0x101724d` | `75 08` | `90 90` |
| 4 | `0x1810187ae` | `0x1017bae` | `75 08` | `90 90` |
| 5 | `0x18101903a` | `0x101843a` | `75 09` | `90 90` |
| 6 | `0x18105a346` | `0x1059746` | `75 0d` | `90 90` |

### 3.2 补丁语义

`jne <非None路径>` → `nop nop` ⇒ 忽略判断结果，**继续执行下一条**（即 `rax == None` 的放行路径）：

```
0x1810169b2  mov rbx, [rdi+0x60]
0x1810169b6  mov [rdi+0x60], rax
0x1810169ba  jmp 0x181017338      ← 跳过弹窗逻辑
```

**零寄存器副作用**（`rax` 后续被使用，尤其第 6 处未预先保存副本，故**不可用 `xor eax,eax` 清零**）。

### 3.3 打补丁的注意事项

1. **必须逐个 xdd 核实原字节后再改**（上表已实测，但改前应再验一次，文件可能被更新）。
2. **PE 校验和**：改后 PE 头 `CheckSum` 会失配。多数程序不检查；若不检查可忽略，否则需重算。
3. **保留原件**：改前复制 `main.dll` 到 `main.dll.orig`。
4. **签名**：若 `main.dll` 有 Authenticode 签名，改后签名失效（但程序通常不验自己）。
