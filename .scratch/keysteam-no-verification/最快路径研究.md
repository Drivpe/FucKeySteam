# 跳过验证弹窗：最快路径研究

**问题**：现在要「最快」达成启动不弹验证码弹窗，该做什么？

**方法**：对 `main.dll` 直接反汇编定位判定点 + 核验票据缓存与补丁实物。本文所有结构性结论都是本次实测，非引用转述。

## 结论先行

**本轮的最终结论是：静态路线已走到尽头，唯一下一步是运行期定位。**

三条曾经被寄予希望的路径，本轮全部在字节层面被否证：

1. **两个现成补丁（`patchA`/`patchB`）不在验证链上** —— 真机对照（三份 DLL 逐帧一致）+ 静态语义定性 + 归属核验三重证据收敛。
2. **在 12KB 校验链主函数里打单点补丁不成立** —— 该函数有 19 处 `je 0x180f99e3e`、33 处失败处理；CFG 可达性证明 patchB 的成功分支**仍可达两个弹窗创建点**。
3. **闸门的机器码根本不在静态文件中** —— 函数对象槽 `0x181dcc130` 位于 `.data` BSS，**写 0 条读 9 条**，磁盘上为零；全 `.text` 中「`lea` 到 `.text` 后接 `MAKE_FUNCTION`」的形态命中数 **0**。

⇒ **「改函数入口」「改函数内分支」「改槽」三条路对闸门全部不成立。** 唯一可操作的是**运行期**：在 `0x180fe1ec7`（闸门定义现场）下断，从 MAKE_FUNCTION 的栈参数解析 `PyCodeObject`，读 `m_code` 得机器码入口。

**本轮的净产出不是答案，而是**：把「该往哪打」这个问题的**全部错误答案排除掉**，并把剩下那条路所需的**全部前置条件**准备完毕（`gate_locate.py` 探针 + 6 个分派点 + 调用约定 + 运行期三条纪律）。

**一条必须记住的时效事实**：`%APPDATA%\Shikieiki\verification.cache`（活票据，sha256 `b044406c…`，605 B，mtime **2026-09-15 14:13:49**）**未被样本刷新**，今天 09-18，**已跨 3 个日界**。按「一票管一天」的设定它已失效——所以「不弹窗」在票据侧**没有现成的可用答案**，必须走改样本路线。

⚠ **勿混淆票据副本**：`_re/cache/verification.cache` 与 `_re/backup/round5-20260915/`、`Shikieiki_orig/` 里的那份是 sha256 `e81e0a54…` 的**已作废旧票**，与活票据 `b044406c…` 内容不同（两份 nonce 不同，是两次独立签发）。**任何「从 `_re/cache` 恢复票据」的操作都会装入一份作废票。** 活票据的 `b044406c` 副本共 3 份：`%APPDATA%`（唯一活体）、`_re/backup/round5-20260915-valid-ticket/`、`D:\ks_probe\_bk\`（只读 `-r-xr-xr-x`）。

## 一、本次实测的新发现（决定了路径排序）

### 1.1 `patchA` 与 `patchB` 打在了完全不同的地方——`patchA` 必然失败

把两个补丁的文件偏移换算到 VA 并查 `.pdata` 函数表：

| 补丁 | 文件偏移 | VA | 所属函数 |
| --- | --- | --- | --- |
| `patchA` | `0xbf1ace` | `0x180bf26ce` | **`0x180bec0d2`–`0x180bf599a`**（与校验链无关） |
| `patchB` | `0xf9923c` | `0x180f99e3c` | **`0x180f99340`–`0x180f9c3de`**（校验链主函数） |

实测命令：

```
$ python3 -c "from binlib import Bin, IB, DEFAULT_DLL; b=Bin(DEFAULT_DLL); \
  print(b.off2rva(0xbf1ace), b.off2rva(0xf9923c))"
```

**判读**：`patchA` 打的 `0x180bf26ce` 与校验链主函数 `0x180f99340` **相距约 290 万字节、跨函数**。它与 `_check_cached_verification` 毫无关系——这解释了为什么它部署后 `RESULT: DIALOG_PRESENT`。此前对 `patchA` 失败的解释（「位于类体方法绑定区、只在导入期执行一次」）方向正确，但更准确的说法是：**它根本没落在校验链所在的函数里**。

`patchB` 的 `0x180f99e3c` **确实在**校验链主函数内。这是它比 `patchA` 明显更接近目标的地方。

### 1.2 但 `patchB` 只堵了 33 个失败点中的一个

对校验链主函数 `0x180f99340`–`0x180f9c3de`（12,446 字节）完整反汇编后的统计：

```
跳到失败出口 0x180f9bf10 的指令数: 20+ 处
call 0x1800e9580（疑似 _failed 处理）: 33 处
```

`patchB` 改的那一处 `0x180f99e3c`：

```asm
0x180f99e39  test rbx, rbx
0x180f99e3c  jne 0x180f99e53      ; ← patchB 改成 eb（无条件跳）
0x180f99e3e  lea rdx, [rbp - 0x80]
0x180f99e45  call 0x1800e9580     ; 失败处理
0x180f99e4a  jmp 0x180f9bf10      ; 跳到函数出口
0x180f99e53  ...                  ; 继续正常流程
```

改 `jne`→`jmp` 只能让**这一个**检查点恒走成功分支。**另外 32 处 `call 0x1800e9580` 与 19 处 `jmp 0x180f9bf10` 原样保留。**

**判读**：这是一个巨型函数，失败路径散布在 12KB 里。单点补丁的期望成功率**很低**——你堵住的那一个检查点，极可能不是运行期真正走到的那个。这与 `patchA` 的教训是同一个：**在定位到真正的判定点之前，改跳转是抽签。**

### 1.3 弹窗的唯一构造点已定位（这是捷径的关键）

用 `rip_refs` 全 `.text` 扫描（444,725 条 RIP 引用）搜 `src.gui.main_window` 的 `mod_consts`（`0x181dc7420`）槽引用，得到：

```
槽 744 VerificationDialog          0x181dc8b60  引用=2
    0x180f9a4eb  mov rbx, [rip+0xe2e66e]   (函数 0x180f99340)
    0x180f9b5fb  mov r15, [rip+0xe2d55e]   (函数 0x180f99340)

槽 742 _fetch_verification_config  0x181dc8b50  引用=2
    0x180f9a3ab  mov r15, [rip+0xe2e79e]   (函数 0x180f99340)
    0x180f9baf6  mov r15, [rip+0xe2d053]   (函数 0x180f99340)

槽 724 _check_cached_verification  0x181dc8ac0  引用=1
    0x180f98d7d  mov rcx, [rip+0xe2fd3c]   (函数 0x180f98cc0)

槽 727 load_verification_ticket    0x181dc8ad8  引用=1
    0x180f995cb  mov r8, [rip+0xe2f506]   (函数 0x180f99340)
```

**关键结构事实**：`VerificationDialog`（弹窗类）在**全样本只有 2 处引用**，都在同一个函数 `0x180f99340` 内。而 `_fetch_verification_config`（缓存不通过才联网）也在这个函数内。

⇒ **`0x180f99340` 就是「票据校验链」的主函数**：它同时办了「读缓存 → 校验 → 失败则联网 → 仍失败则建弹窗」。这与 `docs/probe-repack.md` 画的链条完全对应。

弹窗创建点在 `0x180f9a4eb`，其上游分支是：

```asm
0x180f9a4c0  call 0x181423a80        ; 调用某回调，结果在 rax
0x180f9a4c5  mov r14, rax
0x180f9a4c8  test rax, rax
0x180f9a4cb  jne 0x180f9a4e7         ; rax != 0 → 走到 0x180f9a4eb 建弹窗
0x180f9a4cd  lea rdx, [rbp - 0x80]   ; rax == 0 → 走 _failed 分支
0x180f9a4d4  call 0x1800e9580
0x180f9a4e7  ...
0x180f9a4eb  mov rbx, [rip+0xe2e66e] ; → 0x181dc8b60 = VerificationDialog
```

**这个 `jne`（`0x180f9a4cb`）是弹窗的开关——但方向与直觉相反。**

### 1.4 `rax` 语义已查明：不是「票据有效」，是 `fetch_config()` 的返回值

这是本次会话**推翻任务书假设**的一处发现。`rax` 不是「票据是否有效」的布尔值，而是 **`self.fetch_config()` 返回的验证码配置对象**。

证据（三重互证，直接观测级）：
- 槽 731 = `fetch_config`，从 Nuitka 常量池解出（tag=`0x61`）
- `0x181423a80` 是 Nuitka 的「取属性并调用」thunk，等价 `getattr(obj,name)(arg)`；其失败分支抛的是
  `PyErr_Format(PyExc_AttributeError, "'%s' object has no attribute '%s'")`
  （RVA `0x1d4b8e4`/`0x1d4b8cc`、串 `0x181d0f8c8`，实测）
- `0x180f9a4b2` 载入槽 731（`r8 = [rip+0xe2e63f]` → `0x181dc8af8`），`rdx = [r13+0x10]` 为 self

**字节级实测**：

```
0x180f9a4c8  test rax, rax        ; 48 85 c0
0x180f9a4cb  jne 0x180f9a4e7      ; 75 1a   ← rax!=0 → 建弹窗
0x180f9a4cd  lea rdx, [rbp - 0x80] ; 失败出口（抛异常）
```

`rax != 0`（拿到配置对象）→ **建 `VerificationDialog(initial_config=rax)`**，源码行号 2060。
`rax == 0`（无配置）→ 走 `0x180f99e3e` 失败出口。

**⇒ 改 `0x180f9a4cb` 的 `75 1a` → `eb` 是「无条件建弹窗」，方向反了。** 这是本次分析最容易踩的陷阱：它与 patchB 的 `0x180f99e3c`（也是 `75`）**字节相同、语义相反**，不可互套。

### 1.5 正确的补丁点是 `0x180f99e3c`（patchB 原案）

配对结构实测：

```
0x180f9a46e  call 0x1814232e0      ; 第一次取用 fetch_config
0x180f9a490  test rbx, rbx         ; 48 85 db
0x180f9a493  je 0x180f99e3e        ; 0f 84 a5 f9 ff ff  ← 6 字节，失败出口

0x180f9a4c0  call 0x181423a80      ; 第二次取用（同一槽 731）
0x180f9a4c8  test rax, rax         ; 48 85 c0
0x180f9a4cb  jne 0x180f9a4e7       ; 75 1a  ← 建弹窗

0x180f9a4e7  ...                   ; 到达弹窗创建点 0x180f9a4eb
```

而弹窗创建点 `0x180f9a4eb` 经**反向支配分析穷举前驱**确认**只有唯一条件入口**——这排除了「还有别的路径能到弹窗」的可能。

**patchB 的位置 `0x180f99e3c`（`75 15` → `eb 15`）正是失败出口 `0x180f99e3e` 前的那个 `jne`**，把它改成无条件跳后，执行流**不再落到 `0x180f99e3e`**，而是直接进 `0x180f99e53`（正常流程）。

### 1.5.1 一处让 patchB 比我原先评估更强的关键统计

全 `.text` 穷尽统计（按指令立即数扫描）：

```
跳向共用失败出口 0x180f99e3e 的 je 指令: 19 处
0x180f99fda  0x180f9a16f  0x180f9a27e  0x180f9a384  0x180f9a493
0x180f9a5f5  0x180f9a757  0x180f9a9a0  0x180f9aaaf  0x180f9af8c
0x180f9b253  0x180f9b5d3  0x180f9b6e3  0x180f9b8ba  0x180f9b9c9
0x180f9bacf  0x180f9bbde  0x180f9bce4  0x180f9bdf3

跳向 0x180f99e53（正常流程）的指令: 1 处 —— 就是 0x180f99e3c 本身
```

**读法**：19 条失败路径全部汇入 `0x180f99e3e`，而 `0x180f99e3c` 是**唯一**通往正常流程 `0x180f99e53` 的门。把它改成无条件跳，等价于**一次性绕过全部 19 条失败分支**。

**同时也再次说明 `0x180f9a4cb` 不可动**：它属于那 19 条中的 `0x180f9a493` 之外的**另一支**（`jne` 建弹窗），改它只会让弹窗无条件出现。

### 1.5.2 但 CFG 可达性分析证明：**patchB 仍然不能消除弹窗**

对 `0x180f99340`–`0x180f9c3de` 全函数建控制流图（顺序边 + 全部立即数跳转边），从 patchB 的成功分支 `0x180f99e53` 出发做 BFS：

```
从 0x180f99e53 可达节点数: 2456
   可达 弹窗1 (0x180f9a4eb): True    ← 仍能到弹窗
   可达 弹窗2 (0x180f9b5fb): True    ← 仍能到弹窗
   可达 0x180f99e3e（失败出口）: True
   可达 0x180f9bf10（异常抛出）: True
```

原因在 `0x180f99e53` 之后的代码里就看得见——**紧接着又是一个失败检查**：

```asm
0x180f99e6c  mov r8, [rip+0xe2dc0d]   ; -> 0x181dc7a80
0x180f99e7a  call 0x181423a80         ; 又一次「取属性并调用」
0x180f99e7f  mov rbx, rax
0x180f99e85  test rax, rax
0x180f99e88  jne 0x180f99ea1          ; 成功才继续
0x180f99e8a  lea rdx, [rbp - 0x80]
0x180f99e8e  call 0x1800e9580         ; 失败搬运异常
0x180f99e9c  jmp 0x180f9bf10          ; → 异常出口
0x180f99ea1  ...                      ; 下一个检查点
```

**判读**：patchB 只是把执行流从「第一道失败出口」推到「第一道成功分支」，那之后**还有成串的检查点**，任意一个失败都仍会走到弹窗或异常出口。**单点补丁在这个 12KB 的复合函数里不成立**——这正是 1.2 统计给出的预期（33 处失败处理），现由 CFG 可达性坐实。

⇒ **`patchB` 不构成解法。** 它是一个有价值的排除实验（成本 15 分钟，可坐实此判断），但不是「跳过弹窗」的答案。

### 1.6 硬约束：改槽不可行，只能改 `.text`

槽区位于 `.data` 的 **BSS 未初始化段**，`va2off()` 返回 `None`——**磁盘文件里根本不存在这些指针值**，只在运行期由 `createModuleConstants` 装配。而项目文档已确证进程对自身加了拒绝写 ACL（`PROCESS_VM_OPERATION|PROCESS_VM_WRITE`），运行期内存改写会失败。

**⇒ 「改槽」路线在磁盘与运行期双双不可行，唯一可改的是 `.text` 里的判别指令。**

### 2.1 `patchA` / `patchB` 已被否证，且**根本不在验证链上**

**这是本次会话最重要的否定结果。三条独立证据链收敛到同一结论。**

**证据一：真机对照实验**（三份 DLL 各建独立完整 payload 夹具，跑同一时间线脚本）

| DLL | sha256 前 8 | 弹窗出现 | 主窗 DIS 翻转 |
| --- | --- | --- | --- |
| 原件 | `cc869941` | ~1585ms | False→True |
| patchA | `657b8fe3` | ~1392ms | False→True |
| patchB | `48fd9598` | ~1363ms | False→True |

三者窗口状态机**逐帧完全一致**（出现时间差属加载抖动）。补丁没动验证链 → 弹窗照旧。

**证据二：静态反汇编的语义定性**

- patchA（`0xBF1ACE`，`jne +0x16` → `jmp +0x16`）：判定依据 `test bl,bl`，`bl` 来自 `call 0x180166a90`（`sete al` 布尔取反）。被跳过的分支执行 `mov ebx,0x6bb` 后跳**异常汇合点 `0x180bf5550`**（该函数内 136 处 `jmp` 指向它）。
  **语义 = 抑制错误码 `0x6BB` 的异常抛出，与验证无关。**
- patchB（`0xF9923C`，`jne +0x15` → `jmp +0x15`）：判定依据 `test rbx,rbx`，`rbx` 来自 `call 0x1814232e0` 返回的指针。被跳过分支是**空指针短路返回**。
  **语义 = 强制走正常解引用路径。且补丁后在 `rbx==NULL` 时会执行 `cmp dword ptr [rbx],0` → 访问违例 `C0000005`**——它把「可恢复的空指针」换成了「崩溃」，有崩溃风险。

**证据三：归属核验全部落空**

- `docs/probe-repack.md` 标注 `0x89851C` 为 `verification_dialog` 簇，**实测该处内容是 `src.security.ticket` 的常量池**（`_TICKET_PREFIX`/`aChaCha20Poly1305`/`cskeysteam-ticket-v1`/`usrc.security.ticket`）——**锚点标注与内容不符**。
- 全 `.text` 引用该簇的指令数 = **0**；引用 `_verification_gate_allows` 常量表（`0x1CB2105`）的指令数 = **0**（我用正确的 `VA = IB + 节VA + (file_off - 节raw)` 换算复核，确认零引用是真实结果，非换算错误）。
- 两函数的 `.rdata` 可读串引用分别 0 个和 1 个，与 `verification`/`ticket` 关键词**零命中**；两函数入口在 `.data` 中**均无函数指针引用**，无法经函数表回溯模块归属。

**⇒ 结论：`_re/probe_A/main.dll` 与 `_re/probe_B/main.dll` 不能用来验证「消除弹窗」。它们改的是别处（一个异常守卫、一个空指针短路），不在验证链上。**

**这条否定结果的方法论意义**：Nuitka 经槽表**间接**索引常量、不做指令级 RIP 引用，故**仅靠静态反汇编无法把函数挂到 Python 模块**——需要运行期槽表解析或调用栈采样。这解释了为何本会话多次静态定位闸门字符串（`_verification_gate_allows`）都得到零引用，也说明路径 1 必须走**行为定位/运行期观测**，不能靠静态字符串搜索。

⚠ **两条关键限制**：
1. `verify_patch.ps1` 只能回答「弹窗在不在」，**不能回答「补丁是否生效」**——原件也报 `DIALOG_MODAL_CONFIRMED`。上表的「逐帧一致」才是有效判据。
2. `_re/probe_A/` 与 `_re/probe_B/` **各自只有 1 个文件（main.dll）**，缺 `python312.dll` 等全部依赖。宿主直接 `--dll` 指向它们必然以**退出码 3**失败，必须先放进完整 payload 目录（52 文件）。

### 为什么路径 1 优于路径 3

`_verification_gate_allows` 是 `MainWindowController` 的**独立方法**，`_guard_sensitive_action` 全部经它判定（`KeySteam-无验证运行-落地方案.md` §2）。它的函数体**远小于** 12KB 的校验链主函数——按同一个方法论，它的失败分支数应该是个位数。

**在小的收口点上工作，比在大的复合函数里找判定点，成功率高一个数量级。** 这正是 `_verification_gate_allows` 被当初判定为「唯一收口点」的理由，而这次实测为它补上了可执行的定位手段。

**验证判据（用这个，不要用窗口标题单独判断）**：

⚠ **判据已按真机实测修正**（原字面版会永远判否）：

**关于 `main_disabled` 的准确定性**（实测，含一处对常见说法的纠正）：

**Qt 并不实时维护这个位。** 因此准确定性是：它不是模态栈的实时副产品，也不是 Qt 强制的模态标记，而是**程序自己 `setEnabled(False)` 且从未恢复的诚实读数**。作为「弹窗出现」的伴随判据**可靠**，但**不能说成「模态阻塞的直接证据」**。

**两个仓库级坑**（可能影响其它校验脚本）：
1. `Split-Path -LiteralPath X -Parent` 与 `Join-Path` 在 PS5.1 **和** pwsh7 下都抛 `AmbiguousParameterSet`（`-LiteralPath` 与 `-Parent` 不属同一参数集）。改用 `[System.IO.Path]::GetDirectoryName/Combine`。

### 8.6 已交付的运行期定位探针：`gate_locate.py`

既然 8.3 证明静态字符串搜索必然失败，我把「运行期定位」这条路径做成了**可直接执行的脚本**：

**位置**：`KeySteam v2.99/_re/ghidra/gate_locate.py`

**手段**：对 `getattr+call` 辅助 thunk（RVA `0x1422ec0`，本项目已实测确认 `setModal`/`setObjectName` 的 getattr 都 call 它）下**硬件执行断点**，捕获每一次 thunk 调用，dump `r8`（属性名字符串对象）、`rcx`/`rdx`/`r9` 与**调用者返回地址**。当属性名含 `_verification_gate_allows` / `_guard_sensitive_action` / `_emit_integrity_lock` / `_on_runtime_tamper` 时高亮记录。

**两处针对既有缺陷的刻意修正**（写脚本时已固化，并注明理由）：

## 九、闸门定位的最终结论（本会话最具决定性的技术产出）

### 9.1 闸门的机器码**不在静态文件中**——这是路径性否证，不是「没找到」

**直接观测证据**（两条独立）：

```
槽 368 (0x181dcc130) _verification_gate_allows : 写 0 条, 读 9 条
槽 244 (0x181dcbd50) _guard_sensitive_action   : 写 0 条, 读 5 条
```

- 闸门函数对象槽 = `MC(0x181dcb5b0) + 8×368 = 0x181dcc130`，**位于 `.data` BSS，静态文件里是空的**（`va2off()` 返回 `None`）。
- 闸门的定义现场 `0x180fe1eae`–`0x180fe1eed`：把 5 个**全为 BSS 槽**的值压栈后 `call 0x18140a220`（Nuitka `MAKE_FUNCTION`），返回的函数对象存入 `0x181dcb3b8`。**5 个入参静态读全为 0。**
- 补充否证：全 `.text` 中 `lea r??,[rip+.text]` 后 12 条内 `call 0x18140a220` 的形态，命中数 = **0**。**没有任何一处用立即数直接装载闸门的代码地址。**

⇒ **机器码地址由 `.data` 初始化器在运行期填充。** 因此：
- **「改函数入口」**这条路对闸门**不成立**（没有静态入口可改）；
- **「统计闸门体内的失败分支数」**这个前提**不成立**（函数体不在文件里）。

### 9.2 替代产出：**6 个闸门分派点**（这是可操作的实物）

`self._verification_gate_allows(...)` 走 `getattr + call`，故 `.text` 中**没有直接 call**，只有 6 处按名字分派的现场，**6/6 形态一致**（我已独立复核，引用槽 368 的指令共 9 条：1 写 + 6 分派 + 2 其他）：

| 分派点 | 所属函数范围 | 函数字节数 |
| --- | --- | --- |
| `0x181016997` | `0x1810168e0`–`0x181017500` | 3104 |
| `0x1810175af` | `0x181017500`–`0x181017d8b` | 2187 |
| `0x181017e38` | `0x181017d90`–`0x1810186e8` | 2392 |
| `0x181018799` | `0x1810186f0`–`0x181018f5c` | 2156 |
| `0x181019021` | `0x181018f60`–`0x181019f17` | 4023 |
| `0x18105a334` | `0x18105a1e0`–`0x18105b390` | 4528 |

标准形态（以 `0x18105a334` 为例）：
```asm
0x18105a334  mov r8, [rip+0xd71df5]   ; -> 0x181dcc130 [槽368]
0x18105a33b  mov rcx, rdi             ; self
0x18105a33e  call 0x181422ec0         ; getattr+call helper
0x18105a343  test rax, rax
0x18105a346  jne 0x18105a355
0x18105a348  mov rbx, [rdi+0x60]      ; 异常路径
0x18105a350  jmp 0x18105ac26
```

**`0x181422ec0` 的语义已确证**：`mov rdi,[rdx+8]`（type）→ `mov rax,[rdi+0x90]`（getattro 槽）→ `call rax`。即标准 Python 动态属性查找。

### 9.3 闸门返回值的语义在**机器码层面确证**（重要）

分派点之后的代码：
```asm
0x18105a355  mov rsi, [rip+0x3e37dc]   ; -> 0x18143db38
0x18105a360  cmp rax, rsi
0x18105a363  jne 0x18105a3bb
0x18105a365  ...                       ; rax == None → 放行分支
```

我把 `0x18143db38` 的重定位项解了出来——它的目标是字符串 **`_Py_NoneStruct`**：
```
0x18143db38: raw=0x1d4b806 -> VA 0x181d4b806
  VA 0x181d4b806 内容 = "Z\x06_Py_NoneStruct"
```

⇒ **`rsi` 就是 Python 的 `None` 单例。** 代码 `cmp rax, rsi` 判定「闸门返回值是否为 `None`」——**与文档记载的「受信：返回 `None` → 放行」完全吻合，且这次是在机器码层面确证，不再是文档转述。**

### 9.4 补丁路线的结论

| 路线 | 可行性 | 理由 |
| --- | --- | --- |
| 改闸门函数入口 | **不可行** | 机器码不在静态文件里（9.1） |
| 改闸门体内分支 | **不可行** | 同上，函数体静态不存在 |
| 改槽（BSS 指针） | **不可行** | 磁盘无指针值 + 运行期拒绝写 ACL |
| 改 6 个分派点的判定 | **理论可行但风险高** | 6 处分散、需 6 次等长替换；且改动 `test rax,rax`/`jne` 的语义方向需逐个确认 |
| **改 `0x181422ec0` helper** | **不建议** | 它是通用 getattr 收口点，波及面过大 |
| **运行期定位后再设计补丁** | **推荐** | 在 `0x180fe1ec7` 下断，从 `[rsp+0x20]`/`[rsp+0x28]` 取 MAKE_FUNCTION 的栈参数，解析出 `PyCodeObject`，读其 `m_code`（偏移约 `+0x50`）即得闸门机器码入口 |

**⇒ 闸门的字节级统计与等长补丁设计，必须在那之后才有意义。** 本轮已交付完成该定位所需的全部前置（`gate_locate.py` 探针 + 6 个分派点 + 调用约定 + 三条运行期纪律）。

### 10.1 已确证（直接观测，可复用）
