# 闸门调用链完整还原与补丁可行性判定

**时间**：2026-09-18 16:30
**对象**：`main.dll`（sha256 `cc869941663ed46bc8973bc18415d2cabd6e6fe7127a7d692fda450cdc405265`）

---

## 0. 一句话结论

**6 个闸门分派点结构完全同构，`rax == None` 时直接 `jmp` 跳过弹窗逻辑——补丁点在 `.text` 里、静态可改。但闸门函数本身的机器码地址由 `type+0x110` 在运行时填充，静态改不到。**

⇒ **可行方案：改 6 处分派点的判断（静态）；不可行方案：改闸门函数本体（需运行时）。**

---

## 1. 6 个分派点完全同构（决定性结构证据）

用 `binlib.rip_refs()` 扫出的 9 处读槽中，6 处是分派点。**逐条反汇编，结构完全一致**：

```asm
; 分派点 1 — 0x181016997
0x181016997  mov r8, qword ptr [rip+0xdb5792]   ; -> 0x181dcc130  闸门函数对象
0x18101699e  mov rcx, rdi                       ; rcx = tstate
0x1810169a1  call 0x181422ec0                   ; getattr+call thunk
0x1810169a6  mov qword ptr [rbp+0x7f], rax
0x1810169aa  mov r13, rax
0x1810169ad  test rax, rax                      ; ★ 判断返回值
0x1810169b0  jne 0x1810169bf                    ; 非 None → 弹窗路径
0x1810169b2  mov rbx, qword ptr [rdi+0x60]      ; None → 放行路径
0x1810169b6  mov qword ptr [rdi+0x60], rax
0x1810169ba  jmp 0x181017338                    ; ★ 直接跳走，不触发弹窗
```

| # | 读槽地址 | `call thunk` | 返回值保存 | 判断 | 跳转 |
| --- | --- | --- | --- | --- | --- |
| 1 | `0x181016997` | `0x1810169a1` | `r13, [rbp+0x7f]` | `0x1810169ad` | `jne 0x1810169bf` |
| 2 | `0x1810175af` | `0x1810175b9` | `r12` | `0x1810175c1` | `jne 0x1810175ce` |
| 3 | `0x181017e38` | `0x181017e42` | `r13` | `0x181017e4a` | `jne 0x181017e57` |
| 4 | `0x181018799` | `0x1810187a3` | `rbp` | `0x1810187ab` | `jne 0x1810187b8` |
| 5 | `0x181019021` | `0x18101902b` | `r15, [rbp-0x39]` | `0x181019037` | `jne 0x181019045` |
| 6 | `0x18105a334` | `0x18105a33e` | （未保存） | `0x18105a343` | `jne 0x18105a355` |

**全部模式**：`mov r8,[闸门槽]` → `mov rcx,rdi` → `call 0x181422ec0` → 保存 `rax` → `test rax,rax` → `jne <弹窗路径>`。

**这是 `if _verification_gate_allows(...) is not None:` 的标准编译产物。**

## 2. 分支语义（确证）

### 2.1 `rax == None` → 放行（不弹窗）

```
0x1810169b2  mov rbx, [rdi+0x60]
0x1810169b6  mov [rdi+0x60], rax
0x1810169ba  jmp 0x181017338      ← 直接跳走
```
**整个弹窗逻辑被 `jmp` 跳过。** 完美对应「`rax == None` 就放行」——与机器码层面 `cmp rax, rsi`（`rsi` → `_Py_NoneStruct`）的语义一致。

### 2.2 `rax != None` → 弹窗路径

```
0x1810169bf  mov esi, 0x4e1                  ; 行号 1249
0x1810169c7  mov dword ptr [r12+0x28], esi
0x1810169cf  mov r8, [rip+0xdb4d42]          ; -> 0x181dcb718
0x1810169d6  call 0x181422d70                ; ★ 进入弹窗/警告逻辑
```

行号 `0x4e1` = 1249，可用于对照 Nuitka 的行号表定位源码位置。

## 3. thunk `0x181422ec0` 的内部逻辑（闸门机器码的获取路径）

```asm
0x181422ec0  mov [rsp+8], rbx
0x181422ec5  mov [rsp+0x18], rbp
0x181422eca  push rsi / rdi / r14
0x181422ece  sub rsp, 0x20
0x181422ed2  mov rdi, qword ptr [rdx+8]        ; rdx = 闸门函数对象 → [rdx+8] = ob_type
0x181422ed6  mov rbp, r9
0x181422ed9  mov rsi, rdx
0x181422edc  mov r14, rcx                       ; tstate
0x181422edf  mov rax, qword ptr [rdi+0x90]     ; ★ type+0x90 取方法槽
0x181422ee6  test rax, rax
0x181422ee9  je 0x181422f80
0x181422eef  mov rdx, r8
0x181422ef2  mov rcx, rsi
0x181422ef5  call rax                           ; 第一次调用（descriptor get）
0x181422ef7  mov rbx, rax
0x181422efa  test rax, rax
0x181422efd  je 0x181422ffe
0x181422f03  mov rax, qword ptr [rax+8]        ; 结果对象 → ob_type
0x181422f07  mov r9, qword ptr [rax+0x110]     ; ★ type+0x110 取槽
0x181422f0e  test r9, r9
0x181422f11  je 0x181422fab
0x181422f17  cmp qword ptr [rax+0x118], 0
0x181422f1f  je 0x181422fab
0x181422f25  mov r8, rdi
0x181422f28  mov rdx, rsi
0x181422f2b  mov rcx, rbx
0x181422f2e  call r9                           ; ★ 第二次调用 = 真正的闸门执行
```

**判定**：闸门机器码入口通过 **`type+0x110`** 槽间接取得。该槽在磁盘上是 **BSS（零）**，由 `createModuleConstants` 在启动时填充。

⇒ **闸门机器码地址静态不可知，纯静态改文件改不到闸门本体。**

## 4. 补丁可行性与方案

### 4.1 不可行：改闸门函数本体

原因：机器码入口经 `type+0x110` 运行时解析，磁盘上该槽为零。需在运行时（`0x180fe1ec7` 的 MAKE_FUNCTION 返回后读 `rax`，再按 `m_c_code` 取入口）才能得到。

### 4.2 可行：改 6 处分派点的判断（静态）

**补丁原理**：把 `jne <弹窗路径>` 改为**无条件跳转到放行路径**，等价于「闸门永远返回 None」。

**精确补丁点（文件偏移 = VA − 0x180000000 + 节内偏移）**：

| # | 指令 VA | 文件偏移 | 原字节 | 原指令 | 建议补丁 |
| --- | --- | --- | --- | --- | --- |
| 1 | `0x1810169b0` | `0x1015db0` | `75 0D` | `jne +0x0D` → `0x1810169bf` | `EB 00 90 90` 或改 jump 目标 |
| 2 | `0x1810175c1` | `0x10169c1` | 待核 | `jne 0x1810175ce` | 同上 |
| 3 | `0x181017e4a` | `0x101724a` | 待核 | `jne 0x181017e57` | 同上 |
| 4 | `0x1810187ab` | `0x1017bab` | 待核 | `jne 0x1810187b8` | 同上 |
| 5 | `0x181019037` | `0x1018437` | 待核 | `jne 0x181019045` | 同上 |
| 6 | `0x18105a343` | `0x1059733` | 待核 | `jne 0x18105a355` | 同上 |

**更稳妥的等价补丁**：把 `test rax, rax` 改成 `xor rax, rax`（`31 C0`），强制 `rax = 0` 使 `jne` 永不跳转。优点是**不用改长跳编码、不论跳转距离**。

⚠ **两项必须先做**：
1. **每个补丁点的原字节必须逐条 `xxd` 核实**（上表除第 1 项外均为推测，未读取）。
2. **改后必须重算 PE 校验和 / 或确认 Nuitka 的自完整性检查**（`aIntegrityCheckResult`、`aTAMPERED`、`a_emit_integrity_lock` 常量存在，说明程序**可能自校验代码段**）。若程序校验 `.text`，静态补丁会被 `ais_invalid` 检出。**这是本方案的头号风险，必须先查。**

### 4.3 待验证的关键问题

**程序是否会校验自身 `.text` 段？** 常量段里出现了：
```
aIntegrityCheckResult  aIntegrityState  aTAMPERED
a_emit_integrity_lock  a_guard_sensitive_action  a_on_runtime_tamper
```
这强烈暗示**存在完整性自检**。若它校验代码段哈希，静态补丁会被检出 → 必须同时处理完整性检查，或改走运行时内存补丁。

## 5. 与 kd3 探针的关系

**`call 0x181422ec0` 正是 kd3 下断点的地址**（RVA `0x1422ec0`）。这解释了两件事：

1. kd3 的 500 次命中**确为同一次命中的重复触发**（时间戳挤在 0.153 秒内、寄存器全同）——现在知道该地址是 `getattr+call` 的通用 thunk，被整个程序大量调用，**不是闸门的专用入口**。
2. 闸门调用必然经过该 thunk，故**用该 thunk 定位闸门调用是可行的**，但**用它的命中次数推断闸门被调用次数是不可行的**（噪音占比极高）。
