# 闸门常量池静态可读性——独立复核结论

**时间**：2026-09-18 15:40
**对象**：`main.dll`（sha256 `cc869941663ed46bc8973bc18415d2cabd6e6fe7127a7d692fda450cdc405265`）

---

## 0. 一句话结论

**闸门方法名与整个模块常量都在磁盘上可静态读取。既有记载「闸门相关字符串必须走运行期」只对「在 `.text` 指令操作数里搜引用」成立，对「读字符串本体与常量池」不成立。**

**但闸门槽 `0x181dcc130` 的「读 9 写 0」被独立确证，且我对子代理的闸门创建点结论有修正。**

## 3. 纠正子代理的闸门创建点

子代理称：闸门 `MAKE_FUNCTION` 在 **`0x180fe1e75`**，且「返回值 `rax` 之后没有任何 `mov [rip+...], rax`」。

**实测修正**：

```
0x180fe1e7a  mov r9, [0x181dcc130]   ← 读出**旧**函数对象到 r9（闸门槽，读）
0x180fe1e81  mov edx, 0x528          ← 行号 1320
0x180fe1e96  mov [0x181dca7d8], rax  ← **有写！**（非「没有任何存槽指令」）
0x180fe1eba  mov rcx, [0x181dcb588]
0x180fe1ec1  mov r8d, 0x1000003      ← 函数对象构造固定标志
0x180fe1ec7  call 0x18140a220        ← **这才是闸门的 MAKE_FUNCTION**
0x180fe1ecc  mov r9, [0x181dcbf78]   ← 下一方法
0x180fe1ed3  mov edx, 0x40f          ← 行号 1039（下一方法）
0x180fe1eed  mov [0x181dcb3b8], rax  ← 有写
```

**两处纠正**：
1. `0x180fe1e96` **确实有写槽指令**，子代理「没有任何存槽指令」的表述不准确。
2. 但**子代理的核心结论方向正确**——`0x180fe1e96` 写的 `0x181dca7d8` 槽号 **-443**（相对 `mwc` 基址 `0x181dcb5b0`），落在**前一个池**，属 `main_window` 池（`0x181dc7420`）槽 113。**不是闸门槽**。

**闸门创建点是 `0x180fe1ec7`**（与交接文档原始记载一致！），子代理说 `0x180fe1e75` 是**误把前一条 `MAKE_FUNCTION` 当成了闸门的**。

## 4. 保留的结论（子代理正确）

1. **`Nuitka_FunctionObject` 没有 `m_code` 字段** —— 机器码入口是 `m_c_code`（`function_impl_code` 类型）。其 `m_code_object` 里的 Python 字节码是**哨兵**（`Py_CompileString("def empty(): raise RuntimeError('Compiled function bytecode used')")` 现造桩）。故「解析 `PyCodeObject` 读 `m_code`」**取不到机器码**——交接文档 §2.3 的原方案前提不成立。
2. **Nuitka 调用约定**：`tstate`→RCX，`self`→RDX（仅 `isForCreatedFunction()` 为真时存在），`python_pars`→**R8**。与实测 `mov r8, r14` 一致。**`self` 缺席时 `python_pars` 前移到 RDX**——这条解释了 kd3 中 `rdx` 的异常形态。
3. **RF flag（Intel SDM）**：指令断点是 **fault**，RIP 仍指向断点指令；处理器**不会**替你置 RF。handler 直接返回 ⇒ 立即再次 #DB ⇒ **死循环**。必须由软件在 `CONTEXT.EFlags` bit 16 置 RF。**这从一级来源解释了 kd3 的 500 次重复触发。**
4. **`SetThreadContext` 会静默改写 DR7 的 G0-G3 全局使能位**（MS Learn）⇒ 想靠全局位常驻会失效，须用 L0-L3 本地位（但任务切换会清零，需重新下断）。
5. **tuple items 偏移 `+0x18` 就是 CPython 官方布局**，项目此前「Nuitka 与 CPython 不同」的记载是误读。
6. **`_machine_bound_key` 用 `.digest()`，`_hash_machine_parts` 用 `.hexdigest()[:32]`** —— 两条不同路径，混用会让两组都失败。

---

## 5. 修正后的闸门方案

**原方案**（交接文档 §2.3）：在 `0x180fe1ec7` 下断 → 从 MAKE_FUNCTION 栈参数解析 `PyCodeObject` → 读 `m_code`。**前提不成立**（无 `m_code`）。

**修正方案**：在 **`0x180fe1ec7`** 下断 → MAKE_FUNCTION 返回后**直接读 `rax`**（Nuitka 函数对象指针）→ 按 `m_c_code` 偏移读出机器码入口。

**新增可选路径（本轮发现）**：闸门方法名与模块常量已在磁盘可读（§2），可按 Nuitka blob 格式**静态切分该池段**尝试直接定位闸门的 `CODE_OBJECT`，**完全绕开运行期**。这是比原方案更优的路径，因为不需要调试器。
