# 结论：(C) 混合 —— 票据的**密码学权威纯本地**（Ed25519 公钥内嵌 + ChaCha20-Poly1305 密钥内嵌），但票据必须由**持有私钥的发放方**签发，且启动弹窗的判定链上**没有任何网络依赖**；「远程清单」是另一条独立通道，与票据判定解耦。

**一句话可判**：伪造票据**不需要联网**，但需要**Ed25519 私钥**才能签出合法 `manifest_sig`——而公钥是硬编码常量。若签发侧的私钥可获取（或其密钥派生可复现），伪造路径成立；若私钥不可得，则 `manifest_sig` 这一环构成真正的密码学墙。

## 3. 问题 3：判定权威归属 → **(C) 混合**

### 3.1 三选一的推理

**(A) 纯本地** —— 部分成立：票据判定的**执行**确实是纯本地（无网络调用），但它**不是自证**：`manifest_sig` 必须通过 Ed25519 验签，而公钥是**固定的** `MCowBQYDK2VwAyEASiaXwDqO2Bbt3W3UgA36ZAxq1ZClERx0i2Xw1vS/eoI=`。任何伪造都必须用**对应的私钥**签名。所以"伪造本地票据"不是改字节就能过，而是要签出一个合法签名。

**(B) 服务器权威** —— 不成立：`verify_ticket` 的 import 表只有 3 项，无任何网络库。判定链**可离线完成**。

**(C) 混合** —— **成立，且是本轮唯一正确的归类**。

### 3.2 (C) 的精确条件

票据判定链的**权威归属**是：

```
权威 = Ed25519 私钥持有者（签发方）
执行 = 客户端本地（ChaCha20-Poly1305 解密 + Ed25519 验签 + 本地时钟比较）
网络 = 非必需（UNREACHABLE 时 SKIPPED，不阻断）
```

**独立权威的两条链**（这是本项目最需要厘清的一点）：

| 链 | 判据 | 权威来源 | 断网行为 |
| --- | --- | --- | --- |
| **票据链** | `verify_ticket` → `manifest_sig` Ed25519 验签 + `expires_at` vs `now` | 内嵌 Ed25519 公钥 | 正常运行（纯本地） |
| **完整性链** | `verify_local_installation` → `IntegrityState` | 本地文件哈希 | 正常运行（纯本地） |
| **远程清单链** | `verify_remote_manifest_async` → `RemoteManifestState` | GitHub 上的 `version.json` + 同一 Ed25519 公钥 | `UNREACHABLE` → `SKIPPED`，不阻断 |

**弹窗由"票据链"与"完整性链"决定，与"远程清单链"解耦。** 三条链共用同一个 `verify_mapping_signature` 与同一把公钥，但**判定时机与阻断语义独立**。

## 4. 伪造一张有效票据所需的全部要素

### 4.1 必需要素清单

**要素 1：票据外层编码（确证）**

```
text     = 'kst~' + base64.urlsafe_b64encode(nonce + sealed).rstrip('=')
其中 sealed = ChaCha20Poly1305(key).encrypt(nonce, plaintext, b'keysteam-ticket-v1')
```

- `_TICKET_PREFIX = 'kst~'`（明文，池 `0x1cd41bd`）
- `_TICKET_AAD = b'keysteam-ticket-v1'`（明文，池 `0x1cd41c3`）
- `_NONCE_LENGTH = 12`（池 `0x1cd41d6`）
- `_TAG_LENGTH = 16`（池 `0x1cd41d8`）

**要素 2：ChaCha20-Poly1305 密钥（需从混淆串还原）**

```
key = hashlib.sha256(bytes.fromhex(verification_crypto_key)).digest()
```

`verification_crypto_key` 由 `src.security.obfuscated_strings` 的 `_decode_text()` 派生。该模块的密钥分段**明文可直读**（`0x1cd0680` 段）：

```
6d2c9117e34a5f90   3391aa44c80b1e72   5a17c3e14982d06f   8c21d45e0a7f6bb1
```

`_decode_segment` 算法确证为 `明文[i] = 密文[i] XOR key[i % len(key)]`（双向闭合验证见 §2.2）。**因此 `verification_crypto_key` 完全可由静态还原——解密密钥不构成障碍。**

**要素 3：票据明文 JSON（字段与类型确证）**

```json
{
  "v": <int>,                  // _TICKET_VERSION，与常量 31 比较；池中 'v' (tag=0x77)
  "purpose": "daily"|"sponsor",// PURPOSE_DAILY / PURPOSE_SPONSOR（池 0x1cd3e5b / 0x1cd3e6a）
  "published_at": "<ISO8601>", // 服务器发布时间戳
  "issued_at":    "<ISO8601>",
  "expires_at":   "<ISO8601>",
  "code_hash":    "<str>",
  "manifest_sig": "<base64>"   // ★ Ed25519 签名，覆盖整个 mapping
}
```

日期解析（确证）：`str.replace('Z', '+00:00')` → `datetime.fromisoformat()` → 若 `tzinfo` 为空则 `replace(tzinfo=timezone.utc)`（常量 62/63/65/66/67/69）。

**要素 4：`manifest_sig` 的 Ed25519 签名 —— 这是唯一真正的障碍**

```
签名对象 = canonicalize_signed_mapping(data)   # json.dumps(sort_keys=True, separators=(',',':'), ensure_ascii=?)
签名算法 = Ed25519（cryptography.hazmat.primitives.asymmetric.ed25519）
验证公钥 = MCowBQYDK2VwAyEASiaXwDqO2Bbt3W3UgA36ZAxq1ZClERx0i2Xw1vS/eoI=（硬编码）
签名编码 = base64（b64encode / b64decode）
```

`signing.py` 的池中同时出现 `Ed25519PrivateKey`（`sign_mapping` 方法用）与 `Ed25519PublicKey`（`verify_mapping_signature` 用）。**私钥不在客户端**——`src.security.public_key` 池只有 `MANIFEST_PUBLIC_KEY_PEM` 一个 PEM 常量。`sign_mapping` 是给**签发侧**用的同一份代码。

### 4.2 有效期怎么算

**不由客户端算**。`verify_ticket` 只做：

```
判定 = (now - _SERVER_SKEW_TOLERANCE_SECONDS 容差) <= expires_at
```

- 无固定天数常量（ticket 池整数仅 4/12/16/172，见 §1.3）
- `expires_at` 直接取自票据明文，**任意长度均可**（客户端不校验合理性）
- `issued_at` 存在但不参与判定（仅记录）
- `published_at` 与 `expected_published_at` 仅当调用方传入 `current_published_at` 时参与（每日码票据的"验证码已更新"判定）

### 4.3 可行性判定

| 环节 | 是否可自行完成 | 依据 |
| --- | --- | --- |
| 外层编码 `kst~` + base64 | ✅ 可 | `_TICKET_PREFIX` / `_TICKET_AAD` 明文 |
| ChaCha20-Poly1305 密钥 | ✅ 可 | 混淆串密钥分段明文直读（`0x1cd0680`） |
| 明文 JSON 结构 | ✅ 可 | 字段名 + 类型注解池内直读 |
| 有效期自定 | ✅ 可 | 客户端不校验，直接写 `expires_at` |
| **Ed25519 签名 `manifest_sig`** | ❌ **需私钥** | 公钥硬编码，签名算法 Ed25519 |

**唯一卡点是 `manifest_sig`。** 攻击面由此收窄为三条：

1. **私钥泄露/可推导**——`sign_mapping` 存在于编译产物中，若签发侧私钥曾随某版本分发，或有确定性派生（池中有 `authorization_cw_key_seed`、`authorization_shiki_key_seed` 两个 `_seed` 常量，说明该项目有**种子派生密钥的惯例**），则可复现。
2. **验签路径旁路**——`verify_mapping_signature` 在客户端有 3 个调用点；若某调用点对 `manifest_sig` 缺失/异常有宽松分支（如 `return None` 被当作通过），可绕过。
3. **二进制补丁**——直接改 `verify_mapping_signature` 或 `verify_ticket` 的机器码。`0x181055340`（`verify_ticket` 入口）与签名函数入口均可定位。

**注意第 2 条的旁证**：`signing.py` 池尾出现 `u Ed25519PublicKey | None`（`load_manifest_public_key` 返回类型）与 `Da return  u Ed25519PublicKey | None`——**返回类型可空**。这意味着 `load_manifest_public_key()` 失败时返回 `None`，**其调用方必须显式处理 `None`**；若有任一分支把 `None` 当作"跳过验证"，即构成旁路。这值得单独实证（见 §6）。

## 6. 确证 vs 推测

### 6.1 确证（一级证据，可复现）

1. `verify_ticket` 的 docstring、参数名、局部变量名、常量清单——池内 UTF-8 直读
2. `verify_ticket` **不调用任何网络函数**——import 表仅 3 项（`obfuscated_strings` / `signing` / `cryptography...aead`）
3. 票据格式：`kst~` + urlsafe_b64 + `nonce(12)` + `ChaCha20Poly1305` + AAD `b'keysteam-ticket-v1'`
4. 判定表达式：`expires_at` vs 本地 `datetime.now(timezone.utc)`，带 `_SERVER_SKEW_TOLERANCE_SECONDS` 容差
5. **无固定天数 TTL 常量**
6. 签名算法：**Ed25519** + `canonicalize_signed_mapping`（`json.dumps(sort_keys=True, separators=(',',':'))`）
7. 公钥硬编码，OID 确证为 Ed25519
8. 混淆串 XOR 密钥明文可读，算法确证，URL 全部解出
9. `raw_github_proved` = "raw.githubusercontent.com 可达性标志"，**与验证无关**
10. `RemoteManifestState` ∈ `{PENDING, UNREACHABLE, SKIPPED, VERIFIED, LOCKED, TAMPERED}`，`SKIPPED` 存在
11. `verify_remote_manifest_async` 拉取 `version.json`（`release_manifest_service` 池常量 10）
12. 远程清单链与票据链**共享公钥但判定独立**：门禁 `_verification_gate_allows` 读 `IntegrityCheckResult`，不读 `RemoteManifestState`
13. 闸门槽 `0x181dcc130` 读 9 写 0（与既有记载一致）
14. 任务书给出的"函数名偏移"是池内字符串位置，**不是代码地址**（实测全部落在 `.rdata`）

### 6.2 推测（标注，需进一步验证）

1. **【推测】** `UNREACHABLE` 时**不弹验证弹窗**。依据是 `SKIPPED`/`is_skipped` 常量与 `UNREACHABLE` 同池且语义簇一致，且 `_verification_gate_allows` 不读 `RemoteManifestState`。**严格的做法**是动态验证：断网启动，抓 `RemoteManifestCheckResult` 的实际取值与界面行为。（本轮为只读静态分析，未执行。）

2. **【推测】** `verification_crypto_key` 的具体明文。已确证**派生方式**（`_decode_text` XOR）与**密钥分段**（四段明文），但未逐段完成配对解码——因为该池后半段使用了 `_NAME_KEY_HEX`/`_AUTH_KEY_HEX`/`_MESSAGE_KEY_HEX` 三套**不同**的密钥，且这三套密钥本身也是密文（池 `0x1cd0035`/`0x1cd031b`/`0x1cd049f`）。**投入产出比判断**：既然 XOR 密钥（`6d2c9117e34a5f90` 等四段）已明文可读，解出 `verification_crypto_key` 只差正确的密钥选择逻辑；但**这不改变结论**，因为要素 4（Ed25519 私钥）才是真正的卡点。

3. **【推测】** `sign_mapping` 与 `verify_mapping_signature` 是同一份代码的两个方向，私钥**不在客户端**。依据：`src.security.public_key` 池只有 `MANIFEST_PUBLIC_KEY_PEM` 一个 PEM 常量，无私钥常量。但 `obfuscated_strings` 池中有 `authorization_cw_key_seed`、`authorization_shiki_key_seed` 两个 `_seed`——**若签发侧用种子派生 Ed25519 私钥，则种子可能在同一份二进制里**。**这是最高价值的下一步验证点。**

4. **【推测】** `load_manifest_public_key()` 返回 `Ed25519PublicKey | None`，其 `None` 分支的调用方处理方式未知。若任一调用点把 `None` 当"跳过"，即为旁路。**需反汇编 `verify_mapping_signature` 与 `verify_ticket` 中对返回值的三处判定。**

### 6.3 前提修正汇总（任务书 → 实测）

## 7. 结论

**判定：(C) 混合。**

**执行侧纯本地，权威侧是密钥。** 启动弹窗的判定链（`_verification_gate_allows` / `verify_ticket` / `IntegrityCheckResult`）中**不存在任何网络调用**——`verify_ticket` 的 import 表只有 `obfuscated_strings`、`signing`、`cryptography...aead` 三项。断网时远程清单链走 `UNREACHABLE` → `SKIPPED`，**不阻断票据链**。

**但"伪造票据是否可行"的答案不是简单的"可行"**：

- 外层编码、解密密钥（XOR 密钥明文直读）、明文 JSON 结构、有效期——**全部可自行构造**
- `manifest_sig` 的 **Ed25519 签名**——**需要私钥**，公钥硬编码为 `MCowBQYDK2VwAyEASiaXwDqO2Bbt3W3UgA36ZAxq1ZClERx0i2Xw1vS/eoI=`

**因此伪造路径的三条实际攻击面**（按投入产出比排序）：

1. **二进制补丁**（最确定）：定位 `verify_mapping_signature` 的三处调用点，或直接补 `verify_ticket` 入口 `0x181055340` 内的验签分支。
2. **`None` 旁路**（最有价值）：`load_manifest_public_key()` 返回类型可空，检查调用方是否把 `None` 当通过。
3. **私钥还原**（最彻底）：`obfuscated_strings` 池中存在两个 `_seed` 常量（`authorization_cw_key_seed`、`authorization_shiki_key_seed`），若签发侧私钥由种子派生且种子在二进制内，则可完整复现签发能力，从而生成**真正合法**的票据。

**任务书原设想"伪造本地票据"若指"改字节绕过"，在 (C) 判定下不直接成立**——因为票据不是自证的，它依赖 Ed25519 私钥签发的 `manifest_sig`。这一点是本报告最重要的修正。
