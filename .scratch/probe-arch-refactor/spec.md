## Problem Statement

`_re/ghidra/` 是探针工作区：84 个 Python 脚本，每个都做同一类事——把样本 `main.dll` 装进进程、盯住它、把观察到的行为写进日志。它们是一次次实验长出来的，所以每个脚本都自带一套完整的垫底代码。

结果是：**同一段代码被抄了 35 遍。** 写日志的 `L()`、读目标进程内存的 `rpm()`、从内存里解出 Python 字符串的 `read_pystr()`、给线程设硬件断点的 `set_hwbp()`——这四个函数在几乎每个脚本里都各写一份。

抄写已经产生了实际损失，不是理论风险：

1. **`set_hwbp()` 有三个语义不同的版本，而其中一个文件的注释在说谎。** `hwbp_ctrl.py` 的文档字符串与行内注释共三处声称自己设的是「硬件写断点（RW=01, LEN=11）」，但代码只做 `dr7 |= 0x1`——实际设的是**执行断点**。这个矛盾已经导致过一次误判：读结果时把执行断点的数据当成了写断点的数据。

2. **`read_pystr()` 有两个行为不同的版本，差异已实证。** 一版在固定偏移读失败时回退尝试其他偏移、并过滤不可打印字符；另一版只读固定偏移、不过滤。同一段含脏字节的内存（`b"set\x01Modal"`），前者得到 `b'cleanName'`，后者得到 `b'set\x01ModacleanName'`——**把相邻结构的数据串接进了返回值**。

3. **注释与实现脱节是系统性的。** 三个文件的文档字符串自述是同一份文本（第 1–19 行逐字相同，md5 均为 `dff22394e8fa3156922154ede1013f34`），而它们写的是第三份文件的功能。读者打开任一文件，读到的第一段话就与它实际做的事不符。

4. **改动无从下手。** 目录无 git 历史、零测试、零 CI。改一处要动 35 个文件，且没有任何机制能告诉改的人「你没改坏」。

这 35 个脚本是逆向工作的证据来源——`docs/` 下的结论、票据里的判断，都建立在这些脚本产出的日志之上。当前的重复不仅拖慢维护，还在持续制造「日志说了一件事，脚本实际做了另一件事」这类不可见的错误。

## Solution

**把 `probe_lib.py` 没做完的收口做完。**

`probe_lib.py` 已经存在，已被 43 个脚本 `from probe_lib import *` 使用，并且**它的设计目的就是消除重复**——这一点写在它自己的文档字符串里：`enable_debug_priv()` 的说明记着「唯一实现（#15 收口）：原先 probe_lib.py / ms.py / memread_test.py 三份并存」，`current_process_handle()` 的说明记着「这是坑二的根治点……import 顺序不再影响正确性」。

它当前提供的是**基础设施层**：`CONTEXT` 等结构体、事件码与页保护常量、取进程句柄、提权。**它不含任何业务函数**——所以那四个函数至今仍在 35 个脚本里各抄一份。

本次把这四个函数补进 `probe_lib.py`，让调用方只保留「我要盯哪个地址、过滤什么条件、什么时候开始盯」。

**同时纠正三处已知的注释与实现不符**，避免它们随代码一起进库：`hwbp_ctrl.py` 关于写断点的三处错误注释；`hwbp_ctrl.py` 定义了却从未使用的 `WATCH_DATA`（真正传给断点函数的是 `AUX_RVA`）；三个文件的共享文档字符串。

对使用者而言，变化是：`_re/ghidra/` 从「35 份各自完整的脚本」变成「一个公共库 + 35 份只描述目标和条件的小脚本」。

## User Stories

1. 作为操作者，我希望日志函数只有一个实现，这样改日志格式时不需要动 35 个文件。
2. 作为操作者，我希望日志函数的输出字节与现在完全一致，这样 `_re/backup/` 下的历史日志仍可直接对比。
3. 作为操作者，我希望 `probe_lib.py` 里能查到「读目标进程内存」这个能力，这样我不必再去某个脚本里抄一段。
4. 作为操作者，我希望 `read_pystr()` 只有一种行为，这样我不会因为读的是哪个文件的拷贝而得到不同的字符串解析结果。
5. 作为操作者，我希望统一后的 `read_pystr()` 是**带偏移回退与可打印过滤**的那一版，这样脏内存不会被静默串接进返回值。
6. 作为操作者，我希望 `set_hwbp()` 的断点类型（执行 / 写）是**显式参数**，这样 `hwbp_data.py` 的写断点意图不会被编译成执行断点。
7. 作为操作者，我希望 `hwbp_data.py` 迁移后**明确表达它要设写断点**，这样这个意图第一次在代码里可见。
8. 作为操作者，我希望 `hwbp_ctrl.py` 里那三处说「写断点」的错误注释被改正为「执行断点」，这样下一个读它的人不会被误导。
9. 作为操作者，我希望 `hwbp_ctrl.py` 里定义了却从未使用的 `WATCH_DATA` 被删除或接上，这样「看起来在用、实际没用」的死代码不再存在。
10. 作为操作者，我希望三个文件的共享文档字符串被拆开各写各的，这样每个文件开头讲的是它自己的事。
11. 作为操作者，我希望 `probe_lib.py` 里补齐的 API 设置（`argtypes`/`restype`）被复用，这样 3 个 hwbp 脚本里各自重抄的那 6 行可以删掉。
12. 作为操作者，我希望已经规定「统一在 `probe_lib.py` 定义一次」的常量（如 `EXCEPTION_SINGLE_STEP`）不再被脚本重复定义，这样规定和实现一致。
13. 作为操作者，我希望迁移后每个脚本的日志输出与迁移前**逐行相同**，这样我能用旧日志验证没改坏。
14. 作为操作者，我希望每个脚本的**功能行为**不变——尤其是各脚本的目标地址、页集合、超时、过滤条件，这些是脚本存在的理由。
15. 作为操作者，我希望 `read_pystr()` 的行为统一是**有意的改变**、并被记录下来，这样以后看到命中数变化时知道原因。
16. 作为操作者，我希望 `lf_test.py` 与 `stage.py` **不被本次改动触碰**，它们是静态分析/诊断脚本，时间戳是它们的真实需求。
17. 作为操作者，我希望 `hwbp16.py` **不被本次改动触碰**，它的 `set_hwbp` 签名（复数地址）与其余三个不兼容，是另一条技术路线。
18. 作为操作者，我希望迁移**逐个脚本进行**、每个都能独立验证，这样出问题时能定位到具体哪个文件。
19. 作为操作者，我希望迁移顺序是**先易后难**，这样简单的脚本先验证收口方式可行。
20. 作为操作者，我希望在此之前先给 `_re/ghidra/` 建立一个版本控制基线，这样任何一步改错都能回退。
21. 作为操作者，我希望 `probe_lib.py` 的公开接口是**小而稳定**的，这样 35 个调用方不会因为库内部调整而连锁改动。
22. 作为操作者，我希望库函数接受依赖而不是自己创建依赖（如内存读取能力可注入），这样纯计算部分能在非 Windows 环境下验证。
23. 作为操作者，我希望「纯计算」与「系统调用」在库里分层，这样偏移解析这类逻辑可以脱离 Windows 单独测试。
24. 作为操作者，我希望库的文档字符串说明每个函数的**参数含义与副作用**，这样调用方不必读实现。
25. 作为操作者，我希望这次收口能作为样板，这样 `zd` 组、`cov` 组、`mydbg` 组等其他同源族的重复可以照此推进。

## Implementation Decisions

**扩展现有库，不新建库。** 四个业务函数补进 `probe_lib.py`。理由：该库已存在、已被 43 个文件使用、其文档字符串已声明消重复是它的目的，且它已立下「统一在此定义一次，脚本不得再抄」的规矩。新建第二个库会分裂该约定。

**库保持两层结构。** 基础设施层（结构体、常量、句柄、提权）已有；本次补业务层（日志、读内存、读字符串、设断点）。业务层函数接受基础设施作为依赖而非自行创建，以便纯计算部分可脱离 Windows 验证。

**四个函数各自的处理：**

`L()`（日志）—— **35 份功能等价，零风险统一。** 实测 37 处 `def L(` 中，35 份的输出字节完全相同（差异仅在缩进风格与句柄变量名 `f` / `out_log`）。另 2 处（`lf_test.py`、`stage.py`）带时间戳前缀，**不在本次范围**。统一后不得引入新的参数化点——这 35 份没有任何真实差异需要表达。

`rpm()`（读目标进程内存）—— **三个 hwbp 文件逐字同一**（函数体 md5 相同），直接收编，无参数化需求。

`read_pystr()`（从内存解出 Python 字符串）—— **两版行为不同，本次统一为「带偏移回退 + 可打印过滤」那一版**。这是**有意的行为变更**：统一后 `hwbp_ctrl.py` / `hwbp_data.py` 的字符串解析会比现在更保守，可能改变它们的命中统计。**此变更必须记录为决策**（见下）。

`set_hwbp()`（设硬件断点）—— **三版语义不同，本次将断点类型设为显式参数**。`hwbp16b.py` 与 `hwbp_ctrl.py` 传执行断点；`hwbp_data.py` 传写断点加 4 字节长度。这使 `hwbp_data.py` 的写断点意图第一次在代码中显式可见。

**一个必须记录的设计取舍。** 本次统一 `read_pystr()` 的两版行为，**偏离了「逐位等价优先」的既有决策**（见 `docs/adr/0002`）。该 ADR 的立场是：重构先保留旧行为（含缺陷），缺陷另开票。本次在操作者明确选择下**不采用**该默认，理由是需要取舍的两版中存在明确更正确的一版。此偏离需在 ADR 0002 中登记一条修订，说明「何时统一、为何此处统一」。

**断点编码的正确性归属。** 本次**不修** `Dr7` 编码的两个结构缺陷（无条件抹掉全部 4 个槽导致槽 1–3 静默丢失；从未处理 GD 位 bit13）。它们属于缺陷票的范围，与本次收口正交。库函数必须能**表达**这些缺陷以保持等价（例如提供「是否清空全部槽」的显式参数），默认值匹配现存行为。

**分层的 seam 位置。** 唯一的 seam 是 `probe_lib.py` 的公开接口。35 个调用方全部只经这一个 seam 使用库——不新增第二处。库内部可以有私有 seam 供其自身测试使用，但不暴露给调用方。

**先建版本控制基线。** `_re/ghidra/` 当前无 git 历史。在动手前建立独立仓并做一次初始提交，作为逐脚本迁移的回退点。该仓必须以 deny-list 形式排除样本侧产物（`*.exe`、`*.dll`、`*.pyd`、`*.txt` 日志、`__pycache__/`），且**不得**把样本目录纳入。

> **已完成（2026-09-17）。** 基线建于 `_re/ghidra/`（独立仓，`master`，初始提交 `f16252b`）。
> 217 个文件 / 784K——从 935M 压到 0.08%，纳入 104 py（含 `tools/` 19、`scripts/` 1）、
> 75 bat、29 ps1、4 java（Ghidra 脚本）、3 md、1 cmd。
> 排除 Ghidra 工程（`.rep/` 859M）、IDA 分析库（`.rips`）、运行期日志（94 个 `.txt`，最大 55M）、
> `out/`、`__pycache__/` 及样本侧二进制。
> **双向验证过**：9 类产物全部被拦、6 类代码全部放行；暂存区经危险文件扫描，零样本侧文件混入。
> **备份**：本地裸仓 `_re/backup/ghidra-repo-20260917.git`，已推送并经克隆验证（217 文件、字节一致）。
> GitHub 恢复后可 `git remote add origin` 同步。
>
> 排除规则的依据是 `docs/agents/issue-tracker.md` 记录的教训：本项目的另一仓库曾因
> deny-list 漏掉 `*.lua` / `*.ks`，险些被 `git add -A` 提交。**加新模式时必须两个方向都测。**

**迁移逐个进行。** 每个脚本独立迁移、独立验证，不批量提交。顺序从结构最简单的脚本开始，以先验证收口方式可行。

## Testing Decisions

**什么是好测试（本项目的定义）：** 测**外部行为**，不测实现细节。对本项目即：给定同样的输入，函数的输出必须逐字节相同。不断言内部用了哪个偏移、哪个循环——那些是实现细节，库有权改。

**测什么，分两层：**

**第一层——函数级对拍（可在非 Windows 环境跑）。** 对本库中所有纯计算部分，取旧实现与新实现喂同样的输入，断言输出相等。适用对象：`read_pystr()` 的偏移解析与字符过滤逻辑、`set_hwbp()` 的 `Dr7` 位构造逻辑。这层的价值是**快速**——秒级反馈，不启动任何进程、不触碰样本。

已有先例可循：本次分析已用桩件在 Linux 上复现过 `read_pystr()` 的全部分支、并分离验证过三个版本的 `Dr7` 位构造。这些桩件是测试的先驱。

**第二层——日志对拍（需 Windows 环境，逐脚本）。** 每个脚本迁移后运行一遍，将其日志与迁移前的日志逐行对比，差异应仅来自**有意的行为变更**（`read_pystr()` 统一影响到的脚本）。这是**验证收口的正确方式**——它验证的是「使用者看到的东西没变」，而不是「某个函数没变」。

`_re/backup/` 下已有 9 个轮次备份，含历史日志可供对拍。

**测试基础设施现状（决定本决策的约束）：**

`_re/ghidra/` 当前**零测试、零 CI**——无 `pytest` / `unittest` 导入、无 `tests/` 目录、无 `conftest.py`、无任何 CI 配置文件、无依赖锁文件。需注意：文件名匹配 `test_*.py` / `*_test.py` 会命中 4 个文件（`bp_test.py`、`elev_test.py`、`lf_test.py`、`memread_test.py`），但**它们都不是测试**——零断言、零框架导入，全部是探针脚本。**不要把这三个当作既有测试资产。**

因此第一层测试是本项目**从零建立**的第一批测试。它们应当放在库旁边，可被一个明确的命令运行，且不依赖 Windows。

**验收标准：** 迁移完成后，对每个已迁移脚本运行一次，日志与迁移前逐行一致；对 `read_pystr()` 行为变更所影响的脚本，差异应可解释为「脏数据不再被串接」。

## Out of Scope

**`WaitForDebugEvent` 主循环的提取。** 目录中存在 40 个文件含该调用、约 38 份手写主循环。把它收成一个共享循环是另一件事，范围远大于本次（涉及控制流反转、回调设计），**本次不做**。四个业务函数的收口完成后，主循环会成为目录中最大的剩余重复——届时可照本次的结果评估。

**`Dr7` 编码的两个结构缺陷。** 槽 1–3 静默丢失、GD 位（bit13）从未处理。属于缺陷票，另开。特别是 GD 位——`hwbp_data.py` 是唯一设数据断点的脚本，若该缺陷使其断点从未生效，可能影响既有实验结论，需独立查证。

**`hwbp16.py`。** 它的 `set_hwbp(hThread, addrs)` 是**复数签名**（一次设 Dr0–Dr3 最多 4 个地址），与其余三个文件的单数签名调用约定不兼容；代码相似度仅 0.27，是**异族**。它走硬件执行断点路线，与页保护路线技术手段不同。另开票。

**`lf_test.py` 与 `stage.py`。** 不含 `WaitForDebugEvent`，不是调试器脚本——前者是纯静态分析（解析 `main.dll` 的函数表），后者是一次性诊断（试 `OpenProcess`/`DebugActiveProcess`）。它们的日志带时间戳是该类脚本的真实需求（跑得太快、输出太少，需要墙钟时刻区分多次运行），**不是风格差异**。不纳入本次。

**其他同源族的重复。** `zd` 组（3 份）、`cov` 组（5 份）、`mydbg` 组（2 份）、`drive` 组（5 份）、`bp` 组（2 份）、`hlib`/`memlog_lib` 等已实测确认的同源分组。本次只做 hwbp 组需要的那四个函数，`zd` 组因走页保护路线**不需要其中三个**。其他族照本次样板另行推进。

**清空 `_re/ghidra/` 的历史脚本。** 不删任何文件。归档策略（见 `_re/ghidra/README.md`）不变。

## Further Notes

**`_re/ghidra/README.md` 的分组与实际代码同源性在两处冲突，迁移时以代码为准。** README 的「按技术路线分组」是归档语义（记录决策链演进），实测代码相似度是另一套口径。两处冲突：`hwbp16.py`（README 与其余三个并列，实测异族）；`att2.py`（README 归入 `attach` 系列，实测与 `attach` 相似度 **0.006**，属 `cov` 组）。**按 README 配对会合并错文件、漏掉真该合并的。**

**本仓库的文档纪律必须继承。** `docs/agents/domain.md` 的漂移登记表已记录 **45 条**同类认知错误，其中反复出现的三种：**裸行号引用会失效**（改给复现命令，不引行号）、**邻接不等于归属**（Nuitka 常量池相邻不构成模块边界；同理「都碰 Dr7 字段」不构成同源）、**缺失不等于不存在**（负观测需列出所有活解释，否则不能用来支持论断）。本次分析中，「文件出现在 grep 结果里」被误读为「它实现了那个功能」——属于同一类错误。

**术语归属。** 架构通用词汇（module / interface / depth / seam / adapter / leverage / locality）见 `codebase-design`。`_re/ghidra/` 自身的架构词（族 A / 族 B / 复制体分组 / 逐位等价）已收入 `CONTEXT.md` 的「探针脚本架构」节。样本领域词（弹窗 / 票据 / 完整性）见 `CONTEXT.md` 其余各节——**两套词汇不得混用**。
