# 08 — 分离 `hwbp_data` 零命中的三条活解释（含「写断点编码从未设上」）

**What to build:**

查清 `hwbp_data.py` 从未产生命中**究竟是哪个原因**，并给出第一个**写断点的正对照**。

## 为什么这是一个真缺口

`hwbp_data.py` 是全目录**唯一**设数据断点的探针，而它**从未命中过一次**（两份日志 `hwbpData_d1.txt` / `hwbpData_wa.txt` 均 0 命中，实测确认）。

0 命中**不代表机制正常**——它有三条活解释，至今**未被分离**：

- **H2**：目标地址在观测窗口内确实未被写入
- **H3**：目标地址被**读**过，而写断点本就不捕获读
- **H4**：**写断点的编码根本没设上**

**H4 不可排除**，因为**整个目录不存在写断点的正对照**——没有任何一次「已知发生了写、且被断点捕获」的记录。

对照组的差距是清楚的：同批次、同提权窗口、同一事件循环里，`hwbp_ctrl.py` 出了 400521 次命中、`hwbp16b.py` 出了 474470 次。所以**提权、样本存活、调试事件循环本身都正常**——不正常的是这一个探针。

## 加重证据（本次核实）

**其一，三个 hwbp 脚本都不记录「设断点成功/失败」。** `hwbp_ctrl.py` / `hwbp16b.py` 靠大量命中**反证**了机制有效；`hwbp_data.py` 因 0 命中，**没有任何反证**。即：它连自己有没有设上断点都无从判断。

**其二，一处结构性风险。** `hwbp_data.py` 的断点设在 `code in (3, 2)`（CREATE_PROCESS / CREATE_THREAD）分支内，且要求 `if main_base:`；而 `main_base` **只在 LOAD_DLL 事件里赋值**。主线程的创建事件先于 `main.dll` 加载，故该脚本只对**加载之后新创建**的线程设断点。

对照时间线（实测）：`hwbpCtrl_p1.txt` 在 `@0.048s` 加载 DLL、`@2.208s` 才首次命中——中间有 **2.16 秒**没有命中。若那段时间里没有新线程创建，`set_hwbp` 就**一次都不会被调用**。

**其三，加重的日志代次问题。** 那两份 `hwbpData_*.txt` **出自两代 `hwbp_data.py`**（汇总段标题不同，`-- 属性名 x 调用者 频次 --` vs `-- 写入者频次 --`，后者匹配当前文件）。二者都是 0 命中，不影响本票结论，但**对拍时不得当成同一代**。

## 要做什么

**不需要新写探针。** 两个最小实验即可分离三条解释：

**实验 Q1 —— 分离 H2。** 周期性地读目标地址（`WATCH_DATA[0]`，即 `verification_dialog` 的 `mod_consts`），看它在观测窗口内**是否发生变化**。

- 若**发生变化** → 该地址确实被写过 → H2 排除 → 剩下的解释指向 H3/H4
- 若**不变化** → H2 成立（该窗口内确实没写），但这**不能**单独排除 H4

**实验 Q2 —— 建立正对照，分离 H4。** 手动在该地址上做一次**已知的写操作**，确认写断点**能**捕获它。

- 这是本目录**第一个写断点正对照**，无论结果如何都是净收益
- 若捕获成功 → 机制有效，H4 排除
- 若捕获失败 → **H4 成立**，`hwbp_data.py` 的全部历史观测作废

## 运行环境

需 Windows + 提权。机制见 `../ELEVATION-HOWTO.md`（一次性注册，之后非提权会话可用 `Start-ScheduledTask` 触发）。

执行器带**提权闸**：非提权时立即退出（退出码 1）。**不要绕过它**——非提权下样本会在约 2 秒后崩于 `0xc0000005`，日志看起来「跑了但没结果」，正好会制造本票要消除的那类误判。
