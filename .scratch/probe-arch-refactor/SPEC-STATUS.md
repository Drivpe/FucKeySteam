## 工单 03 引入的 P0 缺陷（已修复）

**症状**：6 个脚本 `NameError: name 'make_L' is not defined` —— `L = make_L(f)` 被放在 `from probe_lib import *` 之前，而 `make_L` 来自该库。

**受损**：`disc16` / `disc16b` / `hwbp16` / `hwbp16b` / `hwbp_ctrl` / `hwbp_data`

**为何静态检查漏掉**：`py_compile` 与 `ast.parse` **都通过**（语法合法，只是运行时 NameError）；而工单 03 的抽样选了 `mydbg3`/`zd_dlg`/`guard_multi`——**恰好都是 import 在前的正确顺序**，避开了全部 6 个坏例子。

**教训**：抽样验证若样本选择有偏差，会让系统性缺陷完全隐形。**抽样必选"边界"而非"典型"。**

**修复验证（两层）**：AST 顶层语句顺序检查全部 36 个脚本损坏 0；真机跑 `hwbp_ctrl`（`EXIT code=0`、日志 50746 字节）与 `hwbp16b`（447 字节、内容正常）——修复前均为 0 字节。

## 工单 06 的诚实结论（值得记录）

本票是唯一含行为变更的票（统一 `read_pystr` 为「有回退 + 有过滤」那版）。**但实测下来，日志层面看不到任何差异。**

根因已查明：`hwbp_ctrl` 与 `hwbp_data` 的日志**对字符串解析不敏感**——`hwbp_data` 命中恒为 0（见 `08`），`hwbp_ctrl` 的属性名记录行为 0 条（见 `11`）。

子代理为排除「零差异即通过」的假阳性，**自加做了一次性 A/B 探针**：在真实样本的同一命中点对 `ctx.R8` 同时求值两版，两次运行（467533 / 416775 次命中）**分歧均为 0**——即本次观测窗口内属性名对象恰好全是干净候选，脏串接场景未被触发。

**所以本票的验收强度落在「函数级对拍 54 条断言」+「A/B 实证」上，而非工单预设的「日志差异可解释」。** 子代理明确报告了这一点，未把零差异包装成有差异。

**行为变更本身是真实的**（函数级对拍证明同一脏内存下两版必然分歧），只是本次运行没触发它。

## 工单 11：一个卡住 `#16` 的功能性缺陷

核实工单 `06` 报告的「属性名记录 0 条」现象时，发现它不是「差异不可见」的原因，而是一个**独立的功能性缺陷**：

`hwbp_ctrl.py` 的 `logged` 计数器被**两处共用**——`*** DW HIT` 行（每命中都打，40 万级）与属性名记录行（**本脚本存在的唯一理由**）。两处都测 `logged < MAX_LOG`（=400），而 DW HIT **先执行**。**前 400 次命中耗尽配额，此后属性名记录的条件永远为假。**

**实测**（9 份正常 `hwbpCtrl_*.txt`）：DW HIT 400 条、属性名记录 **0 条**。汇总段的 `已记录 400 条` **是假的**。

**影响**：`hwbp_ctrl.py` 的设计目的（反查 getattr+call 的属性名）**从未跑通**。票据 `#16` 的实验目标之一（「属性名全量统计」）在此缺陷修好前**不可能达成**。

**这是「负观测有两个活解释」的又一实例**——记录为空既可解释为「属性名没出现」，也可解释为「配额被耗尽」，两者至今未分离。已登记漂移表。

`CONTEXT_DEBUG_REGISTERS` **不是 `probe_lib` 的模块级符号**——它只是 `set_hwbp` 的参数默认值。实测 `from probe_lib import CONTEXT_DEBUG_REGISTERS` → `ImportError`。

而脚本**确实在用它**（`ctx.ContextFlags = CONTEXT_DEBUG_REGISTERS`）。所以 `07` 的第一步不是删定义，而是**先在库里把该常量提升为模块级符号**。已写入工单 07 的前置警告与验收项。

## 工单 07 的前置发现（已核实）

`CONTEXT_DEBUG_REGISTERS` **不是 `probe_lib` 的模块级符号**——它只是 `set_hwbp` 的参数默认值。实测 `from probe_lib import CONTEXT_DEBUG_REGISTERS` → `ImportError`。

**但工单 05 之后，脚本已不再引用它**：`05` 删掉 `set_hwbp` 定义段时，那段的 `ctx.ContextFlags = CONTEXT_DEBUG_REGISTERS` 一并消失。当前三个脚本只剩 `EXCEPTION_SINGLE_STEP` 被引用（它是模块级符号，可安全取用）。

所以该坑的风险比原先估计的小：`07` 只需确认 `CONTEXT_DEBUG_REGISTERS` 确实无引用后删除即可，无需动库。已把这一确认步骤写进 `07` 的指令。
